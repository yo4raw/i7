# リリース告知ツイート作成

i7マネ部屋のリリース内容を、ファンが読んで「使ってみよう」と思える日本語ツイートに変換する。

## このスキルがすること

最新（または指定）のリリースタグの変更点を git から読み取り、要点を絞った告知ツイートを **3案** 出す。アイドリッシュセブンのプレイヤー（=主な利用者）に向けた、親しみやすく分かりやすい文体にする。

リポジトリ直下に `.env` があり `X_ID` と `X_PASS` が入っていれば、**標準スタイル（案2相当）の告知文1本を作成し、確認なしでそのままブラウザ自動操作（Playwright）で X へ自動投稿する**（手順4）。`.env` が無い／認証情報が欠けている場合は 3案の提示までで止め、投稿はしない。

## 1. リリース内容を集める

ユーザーがバージョンを指定しなければ最新タグを対象にする。

```bash
# 最新2つのタグを取得（最新リリースと、その1つ前）
git tag --sort=-creatordate | head -2
# 例: v1.37.0 / v1.36.0 が返る → 直前タグ..最新タグ の差分を見る
git log v1.36.0..v1.37.0 --format='%s'
```

- バージョン指定がある場合はその範囲（`<前タグ>..<指定タグ>`）を使う。
- コミット件名（`feat:` / `fix:` 等）が変更点の一次情報。`feat:`/`fix:` が告知価値の高い変更。`docs:`/`chore:`/`Merge` は基本的に告知に含めない。
- 件名だけで意図が分かりにくい場合は、対応する ADR（`docs/adr/`）や spec（`docs/superpowers/specs/`）の冒頭を読んで背景を補う。
- 内部用語はユーザー可視語に直す（プロジェクト方針）。「カード」→**「衣装」**、共有ブローチ→**「共通ブローチ」**。

変更点が複数あるときは、ファンにとって一番うれしい1〜2点に主役を絞る。全部を詰め込むと読まれない。

## 2. ツイートを書く

### 文体・トーン
- アイナナのプレイヤーに向けた、親しみやすく明るい口調。堅い「リリースしました」より「〜できるようになりました！」「〜が便利になりました🎉」のような体験ベースの言い回し。
- 絵文字は2〜4個程度で雰囲気づくりに使う（🎉✨🎵🎴📊📷 など機能に合うもの）。盛りすぎない。
- 誇大表現（「最強」「完璧」等）は避け、何が便利になったかを具体的に伝える。

### 構成の目安
1. 何が新しく/便利になったか（主役の変更点）
2. （任意）一言の補足や使いどころ
3. ハッシュタグ ＋ サイトURL

### ハッシュタグ・URL
- 末尾に `#アイドリッシュセブン` `#アイナナ` から1〜2個 ＋ `https://i7.yo4raw.com` を付ける。
- ツールの通称「i7マネ部屋」を本文で触れてよい（タグにはしない）。

### 文字数（重要）
Xの上限は280。**日本語は1文字=2、URLは長さに関係なく23** として数える。つまり実質「全角約140字」が上限で、URL(23)とハッシュタグの分を引くと本文は概ね **全角110字前後まで**。各案は必ずこの枠に収め、超えそうなら要点を削る。3案は長さに変化をつける（短め／標準／やや詳しめ）と選びやすい。

## 3. 3案を提示する

次の形式で、文字数（全角換算の概算）を添えて出す。ユーザーが選んで微調整できるようにする。

```
【案1（短め）】
<本文> #アイナナ https://i7.yo4raw.com
（約NN字 / 全角換算）

【案2（標準）】
...

【案3（やや詳しめ）】
...
```

3案はトーンや切り口を少しずつ変える（例: 案1=機能ズバリ、案2=使う場面の提案、案3=丁寧な紹介）。同じ文の言い換えだけにしない。

## 例

**Input**（v1.37.0 の差分）: `feat: スコア計算の編成・スコアを画像(PNG)で共有`

**Output（案の一例）**:
```
スコア計算の編成＆スコアが画像で保存できるようになりました📷✨
推し編成のスクショをそのままシェアできます！
#アイナナ #アイドリッシュセブン https://i7.yo4raw.com
```
（約95字 / 全角換算）

## 4. 投稿する（`.env` に X 認証情報がある場合のみ）

`.env` が無い、または `X_ID`/`X_PASS` が欠けている場合は **3案の提示で終了**し、投稿はしない（「`.env` が無いので投稿はせず下書きのみ出しました」と一言添える）。以下は両方が揃っている場合のみ実行する。

### 4-1. 投稿する文面（確認なしで自動投稿）

`.env` に認証情報がある場合は、**標準スタイル（案2相当）の告知文1本を作成し、投稿前の確認を取らずにそのまま投稿する**（ユーザーの明示指示による運用）。

- 文面は手順2のトーン・文字数ルールに従い、案2相当（機能＋「安定型か上振れ型か」のような比較軸を一言／ハッシュタグ `#アイナナ` `#アイドリッシュセブン` ＋ `https://i7.yo4raw.com`／標準の長さ）で1本にまとめる。
- 投稿した文面は結果報告（手順4-4）でそのまま提示する。3案の列挙は不要。
- 例外で投稿しないのは次の場合のみ: `.env` が無い／認証情報が欠ける（3案提示で停止）、またはログイン時にチャレンジ画面が出た（手順4-3の通り停止して手動フォールバック）。
- ユーザーが「投稿前に確認したい」「この文面で」等と明示した場合は、その指示を優先する。

### 4-2. 認証情報の読み取り

`.env` から `X_ID` と `X_PASS` を読む。**パスワードは画面・ログ・ツイート文・コミット等に絶対に出力しない**（ブラウザのパスワード欄へ入力する用途にのみ使う）。

```bash
# キー名の存在確認のみ（値は表示しない）
grep -qE '^X_ID=' .env && grep -qE '^X_PASS=' .env && echo "ok: 認証情報あり"
```

値は `evaluate`/`read` 等で内部的に取得し、変数として保持する。

### 4-3. ブラウザ自動操作で投稿（Playwright MCP）

`mcp__playwright__*` ツールを使う。手順:

1. `browser_navigate` で `https://x.com/login` を開く。
2. ユーザー名欄に `X_ID` を入力 → 「次へ」。
3. パスワード欄に `X_PASS` を入力 → 「ログイン」。
4. `browser_snapshot` でページ状態を確認する。**2段階認証・確認コード・「不審なログイン」等のチャレンジ画面が出たら、そこで停止**し、ユーザーに「自動ログインがチャレンジで止まったので、手動で投稿してください」と最終文面を添えて報告する（無理に突破しようとしない）。
5. ログインできたら投稿作成（`https://x.com/compose/post` を開く、または投稿ボタン相当をクリック）。
6. 本文入力欄に**確認済みの最終文面**を入力する。
7. 「ポストする」ボタンをクリックして投稿する。
8. `browser_snapshot` で投稿完了（タイムラインに反映 or 完了表示）を確認する。可能なら投稿の URL を控える。
9. `browser_close` でブラウザを閉じる。

### 4-4. 結果報告

投稿できたら「投稿しました」＋（取得できれば）投稿 URL を報告する。チャレンジ等で投稿できなかった場合は、理由と最終文面を提示し、ユーザーが手動投稿できるようにする。

> 注意（この方式の限界）: ID/パスワードによるブラウザ自動操作は、X 側の UI 変更・2段階認証・キャプチャ・レート制限で**壊れやすい**。失敗時は無理をせず手動投稿にフォールバックする。安定運用が必要なら X API（OAuth）方式への移行を検討する。
