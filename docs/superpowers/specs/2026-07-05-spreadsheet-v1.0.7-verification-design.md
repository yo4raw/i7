## 背景と目的

ユーザー提供のスプレッドシート(コピー ID `1UiQ-i2Ofq3DJXz0BOeFsjDId3iVrhedCL1mpIsGzNWk`)は、過去に検証済みの ota-life.com「アイナナスコア計算ツール」の **v1.0.7**(更新履歴: v1.0.6 から「楽曲データ追加・固有ブローチデータ追加・所有ブローチ初期値変更・楽曲データ修正」)。`export?format=xlsx` で全数式付き取得可能なことを確認済み(12 シート・約 13 万式)。v1.0.6 の旧コピー(`1PeVXm...09XwI`)も引き続き取得可能。

一方、本リポジトリには既に以下の資産がある:

- `docs/spreadsheet-spec-v1.0.5.md` — シート単体の完全仕様書(860 行、v1.0.5 ベース)
- `tests/oracle/` — v1.0.6 数式の engine 非依存な忠実移植(独立オラクル)
- `tests/fixtures/golden/spreadsheet-v1.0.6.json` — ゴールデンフィクスチャ
- `tests/unit/score/spreadsheetDiff.test.ts` + `tests/oracle/knownDiffs.ts` — 項目別比較と既知差分の分類
- `docs/spreadsheet-score-calc-diff.md` — 差分レポート(engine `0e73ff4` 時点)

ただし `src/lib/score/` はその後 ADR 0036〜0039(期待値の縮小 rate 加重化・判定ガード/スコアダウン除外・RNG sfc32 化・共有ブローチ容量一本化)で変更されており、**差分レポートと knownDiffs の一部は陳腐化している**。

目的: v1.0.7 を正とした仕様書の全面再検証と、現行 HEAD の実装との比較検証レポートの全面更新。ゼロからの再仕様化ではなく「機械 diff + 独立再導出による既存文書の検証」で徹底性と効率を両立する。

## 判定ポリシー(ユーザー決定)

- **原則: スプレッドシートが正。** 不一致は実装側のバグ候補として報告する。
- **例外: 縮小スキルの開始位置。** 実際の衣装の最小発動回数に合わせる現行実装の挙動が正。この項目はスプレッドシートと差異があっても「意図的差異」として `knownDiffs.ts` と ADR に明記し、実装は変更しない。
- 本ポリシー自体を ADR 0040 として記録する。

## フェーズ構成

### Phase 0 — 機械的数式 diff(スクリプトのみ、エージェント不使用)

v1.0.6 / v1.0.7 の xlsx を Python でパースし、数式レベルで全量 diff。`衣装データ` 等の行方向繰り返し(11 万式)はユニークな R1C1 パターンに正規化して圧縮する。更新履歴の「データ更新のみ」という主張を機械的に検証し、ロジック式の変更が見つかれば Phase 1 の重点対象とする。中間生成物(シート別の数式・値ダンプ)は scratchpad に置き、リポジトリにはコミットしない。

### Phase 1 — 仕様書の全面再検証 + v1.0.7 化(Sonnet サブエージェント並列)

計算ドメイン別(チーム属性値 / センタースキル / スキル発動・効果 / 縮小 / ブローチ / イベントボーナス・特効 / 楽曲・ノーツ / スコア式 / 設定・定数)に Sonnet エージェントを割り当てる。各エージェントは既存仕様書を**読まずに** v1.0.7 の数式から仕様を独立再導出し、その後に既存仕様書と突き合わせて相違点を報告する(既存文書の誤りもここで検出する)。別エージェントによる adversarial verify で読解ミスを潰す。結果を v1.0.7 仕様書として統合する。

### Phase 2 — オラクル・ゴールデン更新

`tests/oracle/` を v1.0.7 に追随させ(Phase 0 の diff 結果に基づく。想定は所有ブローチ初期値・データ追加のみ)、v1.0.7 シートのエクスポート時点の計算済み値からゴールデンフィクスチャを再生成する。オラクルとシート実測値の bit-exact 一致を確認してからフィクスチャを確定する。

### Phase 3 — 現行 HEAD との比較検証(Sonnet サブエージェント並列)

`spreadsheetDiff.test.ts` を現行実装に対して再実行し、仕様項目ごとに `src/lib/score/`(`teamBuilder.ts` / `simulation.ts` / `broachResolver.ts` 等)と突き合わせて判定表を全面更新する。`knownDiffs.ts` の既知差分分類も ADR 0036〜0039 後の実態に合わせて棚卸しする。縮小開始位置は判定ポリシーに従い「意図的差異」として分類する。

## 検討した代替案

- **案 A(当初): ゼロから 13 万式を仕様化** — 既存資産(860 行仕様書 + オラクル)の存在が判明したため棄却。重複作業が大きい。
- **案 B: 数式解析のみ(数値照合なし)** — 読解ミスの検出手段がなく棄却。
- **案 C: 数値ブラックボックス照合のみ** — 差異の原因箇所が特定できず棄却。
- **採用: 機械 diff + 独立再導出による既存文書検証 + オラクル/ゴールデン更新** — 徹底性(全ドメイン独立再導出 + 数値照合)と効率(差分ベース)を両立。

## 制約・リスク

- ゴールデンケースはエクスポート時点のシート状態 1 通りのみ(シートへの書込権限なし)。数値照合は当該編成での中間値・最終値の照合となる。
- モンテカルロ部分はシートに存在しないため数値照合不可。理論値・期待値の式レベル検証に留める。
- 丸め・端数処理(ROUNDDOWN 等)の位置が最重要ポイント。仕様書では数式ごとに明記する。
- v1.0.6 旧コピーはユーザー所有ではないため、いつアクセス不能になるか不明。Phase 0 で必要な抽出は本作業内で完了させる。

## テスト方針

- オラクル更新後、`spreadsheet-v1.0.7.json` ゴールデンで bit-exact 検証(既存 v1.0.6 の枠組みを踏襲)。
- `spreadsheetDiff.test.ts` は「match / known-diff / unexpected」の 3 分類を維持し、unexpected をテスト失敗とする回帰ガードを継続する。
- 既存の `tests/unit/score/` スイートは全て green を維持する。
