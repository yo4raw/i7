# 仕様解説ページ §4: 期待カバー率の明示と「縮小 vs スコアアップ」戦略比較の設計

- 日付: 2026-07-07
- 対象: `src/pages/score-calc/spec.astro` §4（判定縮小スキル）、`src/lib/score/specDiagrams.ts`、`src/lib/score/specDemo.ts`
- 関連 ADR: [0044](../../adr/0044-spec-shrink-strategy-visual.md)、前提 ADR: 0043（仕様解説ページ全面リデザイン）

## 背景

ユーザーから「仕様解説ページに掲載されている縮小スキルのスコア寄与（+294,534）が異様に低く見える」との指摘があった。調査の結果、計算エンジンは正しく（MC 平均 277,507 と整合、ライト倍率も対象素点合計に織り込み済み）、原因はページの見せ方にあると特定した:

1. **§4-3 が「全発動カバー率 100%（キャップ済み）」を大きく表示**しているのに対し、
2. **§4-4 の期待値 +294,534 は「発動確率 per を織り込んだ期待カバー率 66.74%」で計算**されており、
3. その **66.74% がページのどこにも表示されていない**。

読者が §4-3 の 100% を §4-4 の式に代入すると 762,905 × 0.6 ≈ 457K になるはずが 294K と表示され、約 36% 低く見える。これが違和感の正体。

さらに、スコアアタックの基本戦略（縮小カバー率 100% 以上の確保が先、スコアアップ神発動は上乗せ）と、その根拠となる「縮小はスコアアップより 1 枚あたりの寄与が大きく、属性値が高いほど伸びる」という比較がページに存在しない。

### デモ編成の実測値（設計判断の根拠）

| 比較軸 | スコアアップ（4枚） | 判定縮小（2枚） |
|--------|------------------|----------------|
| 期待値・デッキ合計 | 286,771 | 294,534 |
| 期待値・1枚あたり | 67K〜77K | 143K〜152K（約 2 倍） |
| 理論最大・1枚あたり（単独想定） | 118K〜192K | 361K〜393K（約 2〜3 倍） |

**デッキ合計では 4 枚 vs 2 枚で相殺されて縮小優位が見えない**。優位性は「1 枚あたり」「1 発動あたり」の比較軸と「属性値スケーリング」（縮小 = 素点比例、スコアアップ = 固定値）で初めて可視化できる。

## ゴール

1. §4-3 → §4-4 の数値の飛躍を解消し、「全発動カバー率」と「期待カバー率」の 2 種類が図と式の両方で区別されて見えるようにする
2. スコアアタックの基本戦略を明文化する
3. 縮小がスコアアップより 1 枚あたりでどれだけ得点寄与するか、なぜ属性値が高い編成ほど差が開くかをビジュアルで伝える

## 変更内容

### 1. §4-3 カバー率図の 2 段バー化（`coverageDiagramSvg` 拡張）

現行の全発動カバー秒バー（169秒 → 100% キャップ）の下に、**期待カバー秒バー**（per 織り込み、66秒 = 66.74%）を追加した 2 段構成にする。

- 上段: 「全発動できた場合」ラベル + 現行の per-card セグメント積み上げ + 100% キャップ表現（変更なし）
- 下段: 「発動確率 per を織り込んだ期待値」ラベル + per-card 期待カバー秒（`カバー秒 × per/100`）のセグメント積み上げ + パーセント表示
- 期待カバー率の数値は `demo.coverage.expectedCoverageRate` / `expectedCoveredSeconds` から渡す（数値直書き禁止、ADR 0043 準拠）

### 2. §4-4 数値例の 2 段構成化

本文を以下の 2 行構成に書き換える（数値はすべてビルド時計算）:

> - 全発動できれば: 対象素点合計 × 0.6 × **100%** = **+441,360**
> - 実際は発動確率があるため: 期待カバー率 **66.7%** → 期待値 **+294,534**

- 「全発動時の上乗せ」は `calcMaxBaseTotal` 内の shrinkMax と同じ按分式の合計値。specDemo に **`shrinkMaxBonus`**（= maxScore 経路の縮小上乗せ合計）を追加してページへ渡す
- `shrinkFormulaSvg` の「カバー率」ボックス注記は現行の小さな括弧書きから、「全発動時 = 100% キャップ / 期待値 = 期待カバー率」の 2 行明記に変更

### 3. §4-5「スコアアタックでの位置づけ」新設

§4-4 の後に新サブセクションを追加し、以下を置く。

#### 3-1. 戦略コールアウト

現行「キューイング仕様」と同じ orange コールアウトのスタイルで:

> **スコアアタックの基本戦略**: 判定縮小はスコアアップより 1 枚あたりの得点寄与が大きく、チーム属性値が高いほど寄与が伸びる。まず縮小でカバー率 100% 以上を確保し（発動ムラに備えて余裕を持たせる）、その上でスコアアップスキルが全発動（神発動）するのを狙うのが基本。

#### 3-2. 1 枚あたり寄与の横棒比較図（`skillContributionCompareSvg` 新設）

デモ編成 6 枚の「期待値寄与」「理論最大寄与（単独想定）」を横棒で並べる。縮小 2 枚（slot0/slot3）は縮小段階色（orange）、スコアアップ 4 枚は amber で塗り分け、縮小の棒が突出して長いことを一目で見せる。

- データは既存の `demo.slots[].skillExpected` / `skillMax` をそのまま使用（配管追加なし）
- 「単独想定」の注記（複数縮小の合成とは一致しない）を図の下に付す

#### 3-3. 属性値スケーリング線グラフ（`skillScalingChartSvg` 新設）

x 軸 = チーム属性値倍率（1.0×〜3.0×、イベント特効相当）、y 軸 = スキル期待値寄与。

- 縮小合計: 右肩上がりの直線（素点比例）
- スコアアップ合計: 水平線（固定値加算）
- データはビルド時に `ComputedTeam` の Shout/Beat/Melody を倍率スケールしたコピーで `calcExpectedScore` を数点（1.0 / 1.5 / 2.0 / 2.5 / 3.0）呼んで生成し、specDemo に `scalingPoints` として追加する
- 「特効で属性値が伸びるスコアタ編成ほど縮小が優位になる」根拠の図解と本文で位置付ける

### 4. specDemo.ts への追加フィールド

```ts
interface SpecDemo {
  // 既存 …
  /** maxScore 経路の縮小上乗せ合計（§4-4 全発動時表示用） */
  shrinkMaxBonus: number;
  /** 属性値倍率別のスキル期待値寄与（§4-5 スケーリング図用） */
  scalingPoints: { factor: number; shrinkExpected: number; scoreUpExpected: number }[];
}
```

- `shrinkMaxBonus` は simulation.ts の按分ロジックを再実装せず、エンジン側の `calcMaxBaseTotal` を内訳（baseScore / scoreUpMax / shrinkMax）を返す形に拡張して取得する（既存呼び出し元は合計値をそのまま使えるよう互換を保つ）。二重実装によるズレを禁止する
- 属性値スケールは `ComputedTeam` の属性値フィールドのみ変更したシャローコピーで行う（カード再計算不要。センタースキル・ブローチは元の値に含まれたままで良い — 「編成全体が per 倍強くなったら」という近似で十分）

## エラーハンドリング

- デモ編成に縮小が含まれない場合は既存どおり `buildSpecDemo()` が throw してビルド失敗
- スケーリング点の計算は既存エンジン関数のみ使用のため追加のエラー系なし

## テスト

- `tests/unit/score/specDiagrams.test.ts`: 新設 2 図 + 拡張 1 図のスナップショット/構造テストを追加（既存の各図テストと同形式）
- `tests/e2e` `score-calc-spec.test.ts`: §4-5 見出しと戦略コールアウトの表示、期待カバー率数値の表示を検証する項目を追加
- specDemo の新フィールドは「期待値合計との整合（scalingPoints[factor=1.0] ≒ expected）」を単体テストで検証

## 非スコープ

- 期待値モデル自体の変更（ライト倍率の位置相関の織り込み等）は行わない — エンジンは MC と整合しており正しい（本設計の調査で確認済み）
- §4-3 図の分母を実効秒数（98.9 秒）へ変える案（案C）は不採用。「先頭除外の秒換算」という追加概念で図が複雑になるのに対し、implementation detail は既に `<details>` 実装詳細に記載があるため
- スコア計算ページ本体（score-calc）の表示変更はしない
