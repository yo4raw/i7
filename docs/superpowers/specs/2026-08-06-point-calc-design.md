# ポイント芸計算ツール 設計

- 日付: 2026-08-06
- 関連 ADR: [0049](../../adr/0049-point-calc-tool.md)
- 参照元スプレッドシート: `1hVilwOeLHvrkqburgdbAypQSj1p58VFZYwBjKRais08`（作成者 @SachiTgr）
- 参照記事: https://note.com/i7a3ganbaru/n/nc24b4d8e9acc

## 1. 背景と目的

「ポイント芸」とは、ポイント系イベントの最終獲得ポイントを `7,777,777` のような狙った数字にぴったり揃える遊びである。フォロワーと数字を並べてイベントを締められる。

既存の実現手段は上記スプレッドシートで、以下の運用になっている。

1. `目標pt` と `現在pt` を入力し、差異を出す
2. 下部の「1ライブあたり獲得pt表」から使うセルを目で探す
3. `= 差異 − (F16*3 + J19*3)` のように手で式を書き、0 になるまで組合せを試行錯誤する

本ツールは 3 の試行錯誤を自動化する。差異を入力すると、ぴったり 0 にできる「★・難易度・プレイ方法・特効%・編成・倍率 × 回数」の組合せを、ライブ回数の少ない順に複数提示する。

## 2. 参照スプレッドシートの解析結果

シートは 11 枚（イベントごとに 1 枚）。各シートの構造は共通で、

- 上部: `目標pt` / `現在pt` / `差異` と、手書きの `= 差異 − (セル×回数 + …)`
- 下部: 1 ライブあたり獲得 pt 表
  - 行 = ★1〜★5 × EASY/NORMAL/HARD/EXPERT（20 行）。A 列は各★に該当する楽曲名の注記のみで、pt には影響しない
  - 列 = 特効ボーナス% × プレイ方法（放置 / FC / オート / PC）
  - 別に微調整用の「SR以下/Lv1（放置）」「SSR1枚・特訓なし/Lv1（放置）」の 2 列

### 2.1 導出した計算式

全 11 シートの表は次の式で完全に再現できる。

```
獲得pt = floor(グレードpt × (1 + 特効率)) + ユニットボーナス + コンボボーナス

グレードpt = floor(基礎点[難易度] × 楽曲★倍率 × プレイ係数)
```

| 定数 | 値 |
|------|-----|
| 基礎点 | EASY 550 / NORMAL 650 / HARD 750 / EXPERT 1000 |
| 楽曲★倍率 | ★1 1.20 / ★2 1.23 / ★3 1.25 / ★4 1.28 / ★5 1.30 |
| プレイ係数 | 放置 0.12 / FC 1.0 / PC 1.0 / オート 1.0（**オートのみ★倍率を掛けない**） |
| ユニットボーナス | MAX編成 270 / SSR1枚・特訓なし・Lv1 10 / SR以下・Lv1 0 |
| コンボボーナス（放置） | 0 |
| コンボボーナス（オート） | 300 |
| コンボボーナス（FC） | EASY 440 / NORMAL 465 / HARD 491 / EXPERT 555 |
| コンボボーナス（PC） | EASY 465 / NORMAL 495 / HARD 525 / EXPERT 600 |

倍率ライブ（2倍 / 3倍）は上記で求めた 1 回分の pt をそのまま整数倍する。

### 2.2 検証結果

全 11 シート・5,109 セル（特効%列 4,809 セル + 弱編成 2 列 300 セル）に対して式を突き合わせた結果、**5,082 セル（99.47%）が一致**した。弱編成 2 列（`SR以下/Lv1`・`SSR1枚・特訓なし/Lv1`）は 300 セル全一致。不一致 27 セルはすべて特効%列にあり、いずれもスプレッドシート側の入力ミスと判断した。

| セル | 内容 | 判断根拠 |
|------|------|----------|
| `N17`（アイスタ⑧用 / Sugao①用 / Sugao②用 / IDOL STAR LIVE用） | ★2 NORMAL FC 60% が `2031` | 他 6 シートの同条件は `2013`。桁の入れ替わり |
| `AH24` 相当（バディナナ用 / 吉兆用 / LaStiara②用 / ISL②用 / LaStiara用） | ★4 EASY PC 180% が `8188/3 = 2729.33…` | 非整数。正しくは `8118/3 = 2706` |
| `Y*` / `Z*`（Sugao①用 / Sugao②用の★1行と★5 EASY） | 200% 列に 210% の値が入っている | 隣の 210% 列（`AA` / `AB`）と同値 |

**この 27 セルはツール側では再現しない。** ただしゴールデンフィクスチャ（`tests/fixtures/point-calc-golden.json`）が対象にするのは、非公開の隠しシート 3 枚（`アイスタ⑧用` / `マリマリ用` / `Sugao用`）を除いた公開 8 シートのみである。隠しシートは htmlview のシートスイッチャーから gid を取得する手段がなく、また pt 表の内容は公開シートと重複するため実害はない。公開 8 シートでは合計 4,449 セル中 4,423 セルが式と一致し、残る 26 セル（上表のうち `アイスタ⑧用` の `N17` を除いたもの）を `knownSheetErrors` として理由付きで記録し、「ツールの出力が正しい値と一致し、かつシートの値とは一致しない」ことをテストで固定する。将来シート側が修正されても差分を追える形にする。

### 2.3 浮動小数点の落とし穴

`floor(グレードpt × (1 + 特効率))` を JavaScript の浮動小数点で素直に書くと、`660 × 2.3 = 1517.9999999999998` となり `floor` が 1517 を返し、正解の 1518 から 1pt ずれる。解析時に実際に 124 セルがこの原因で不一致になった。

**実装は必ず整数演算とする**: `Math.floor(gradePt * (100 + bonusPct) / 100)`。`bonusPct` は整数パーセントで保持する。

### 2.4 特効%とイベントデータの対応

シートの特効段階は `public/events/events.csv` の `special{1,2,3}_gpt_up` から導ける。

- イベント ID 235「BUDDY NIGHT NARRATIVE【BUDDY.3 夢幻】」= `バディナナ用` シート
- `gpt_up: 50 / 20 / 5` = シートの「特効 50% / 準特効 20% / 準々特効 5%」
- 6 スロット（フレンド含む）分の合計が特効率。フル特効 = 50 × 6 = 300%

シート間の差分は「イベントの特効刻み」と「各★の楽曲名」だけで、**pt 表そのものはイベント非依存**である。

## 3. スコープ

### 含むもの

- 差異ぴったりの組合せを自動探索して複数提示する
- ★ × 難易度単位で扱う（楽曲名は扱わない。pt に影響しないため）
- プレイ方法 4 種（放置 / オート / FC / PC）。**PC（パーフェクトコンボ）は実際に出すのが難しいため既定 OFF** とし、チェックボックスで有効化できる
- 編成 3 種（MAX / SSR1枚Lv1 / SR以下Lv1）
- 倍率ライブ 1 倍 / 2 倍 / 3 倍
- 特効% は既定値を自動投入した上でユーザーが編集可能

### 含まないもの

- 所持衣装（`i7_card_counts`）と連動した「実際に組める特効%」への絞り込み
- イベント別の対象楽曲リスト
- スタミナ消費・ステラストーン等の残量管理
- スプレッドシート下部にあった日別ペース管理表（隠しシート `Sugao用` 相当）

## 4. アーキテクチャ

完全静的サイトの原則に従い、計算はすべてクライアントサイドで行う。

```
src/lib/pointCalc/
  types.ts        Difficulty / PlayMode / UnitPreset / LiveSpec / SolverInput / SolverResult
  constants.ts    2.1 の定数テーブル
  engine.ts       livePoint(spec) → number（整数演算のみ）
  candidates.ts   設定 → 候補 LiveSpec 一覧（同一 pt 値は代表 1 件に集約）
  solver.ts       メイン周回 + 端数 DP
src/components/PointCalc.svelte
src/pages/point-calc/index.astro
```

### 4.1 engine.ts

```ts
export interface LiveSpec {
  stars: 1 | 2 | 3 | 4 | 5;
  difficulty: 'EASY' | 'NORMAL' | 'HARD' | 'EXPERT';
  playMode: '放置' | 'オート' | 'FC' | 'PC';
  bonusPct: number;      // 整数パーセント 0..300
  unit: 'max' | 'ssr1' | 'weak';
  multiplier: 1 | 2 | 3;
}

export function livePoint(spec: LiveSpec): number;
```

`livePoint` は副作用も外部依存もない純関数。単体テストとゴールデンテストの対象はここに集約する。

### 4.2 candidates.ts

有効化されている プレイ方法 × 編成 × 倍率 × 特効%リスト × 20（★×難易度）を展開し、`livePoint` を評価する。同じ pt 値になる `LiveSpec` が複数ある場合は、探索効率のため代表 1 件に集約し、他は「同値の別手段」として結果表示時に参照できるよう保持する。

なお弱編成（`ssr1` / `weak`）はスプレッドシート同様、**放置とのみ組み合わせる**（弱編成でオートやフルコンボを取る運用は現実的でないため）。

規模の目安: 特効% 3 種・PC OFF の場合で 20（★×難易度）× 3（放置/オート/FC）× 3（特効%）× 3（倍率）+ 20 × 2（弱編成の放置）× 3（特効%）× 3（倍率）= 900 展開、ユニーク pt 値は 500 前後。

### 4.3 solver.ts（案A: メイン周回 + 端数 DP）

差異 `D` は数百万に達しうる一方、候補 pt 値の最大は 2 万弱。`D` 全体を coin-change DP にかけると `D × 候補数` ≈ 70 億ステップとなり非現実的なため、2 段構えにする。

1. **メイン周回を決める**
   ユーザーが明示指定していればそれを使う。未指定なら候補中の最大 pt 値を採用する。1 回あたりを `M` とする。
2. **周回回数を決める**
   `k = floor(D / M)` から始め、`k, k-1, k-2, …` と減らしながら残差 `R = D - k * M` を作る。`R` は `M` 未満から始まり、`k` を 1 減らすごとに `M` ずつ増える。
3. **残差を最小回数でぴったり構成する**
   `R` に対して unbounded coin change の最小枚数 DP（配列サイズ `R+1`、遷移は候補 pt 値ごと）を解き、経路復元で内訳を得る。計算量は `R × 候補数`。`k` を減らす回数の上限を 2 とし、さらに超過側の近似解を作るためメイン 1 回分の余裕を足すので、`R` は最大でも `(2+2) × M` ≒ 7.3 万に収まる。DP は `0..R上限` を 1 回計算すればすべての `k` について答えが得られる。
4. **ランキング**
   得られた「メイン `k` 回 + 調整 `m` 回」を**残差の小さい順（ぴったりが先頭）、同じ残差ならライブ回数の少ない順**に並べ、上位を提示する。回数を第一基準にすると、1 回多く叩けばぴったりになる場面でズレた解が上に来てしまうため。

`R` をぴったり作れない場合がある（候補 pt 値の最大公約数の都合）。DP は `0..R上限` の全額について最小枚数を同時に求めるため、`R` が到達不能なら**到達可能な直下の値と直上の値の両方**を解として出し、**「残り ±n pt」を明示した近似解**として返す。0 にできないものを 0 と言い張らない。直下だけを見ると、候補が 100pt のみで差異が 7pt といった場面で「0 回で残り 7pt」しか作れず結果が空になってしまうため、超過側も必ず出す。

`solver.ts` は副作用のない純関数として書く。Web Worker 化は**行わない**。最悪ケース（特効% 49 種・ユニーク pt 値 3,916・`R上限` 59,752）を Node で実測して 480ms だったため、メインスレッド同期実行で許容できると判断した。退行検知のため単体テストに 3 秒の上限を入れる。

## 5. UI

`/point-calc/` に単一ページを追加する。ナビゲーションにも追加する。

### 5.1 入力

| 項目 | 既定値 | 操作 |
|------|--------|------|
| 目標pt | 空 | 数値入力 |
| 現在pt | 空 | 数値入力 |
| 差異 | 目標 − 現在 の自動計算 | 読み取り専用 |
| 特効%リスト | 開催中のポイント系イベントの `gpt_up` から生成した達成可能段階 | チップ形式で追加・削除・数値編集 |
| 編成 | 3 種すべて有効 | 個別 ON/OFF |
| プレイ方法 | 放置 / オート / FC が有効、**PC は既定 OFF** | 個別 ON/OFF（チェックボックス） |
| 倍率 | 1 / 2 / 3 倍すべて有効 | 個別 ON/OFF |
| メイン周回 | 自動（最大 pt） | ★・難易度・プレイ方法・特効%・倍率を明示指定可 |

開催中のポイント系イベントが無い場合は、特効%リストの既定を `0, 5, 20, 50, 100, 150, 200, 250, 300` とする。

### 5.2 出力

残差の小さい順（ぴったりが先頭）、同じ残差ならライブ回数の少ない順に候補を並べる。各候補は内訳を行で示す。以下は差異 7,777,777、特効% を `0 / 150 / 300`、PC を OFF にした場合に本方式が実際に返す結果（プロトタイプで確認済み）。

```
差異 7,777,777 pt                                              ぴったり

候補1  合計 432 回
  ★5 EXPERT / FC   / 300% / 3倍 / MAX編成      18,075 pt × 430 回   7,772,250
  ★1 NORMAL / FC   / 150% / 2倍 / MAX編成       5,370 pt ×   1 回       5,370
  ★2 EXPERT / 放置 /   0% / 1倍 / SSR1枚Lv1       157 pt ×   1 回         157
  ────────────────────────────────────────────────────────────
  合計 7,777,777 pt  （残り 0 pt）

候補2  合計 432 回
  ★5 EXPERT / FC   / 300% / 3倍 / MAX編成      18,075 pt × 429 回   7,754,175
  ★3 EXPERT / FC   / 300% / 3倍 / MAX編成      17,475 pt ×   1 回      17,475
  ★1 HARD   / FC   / 150% / 2倍 / MAX編成       6,022 pt ×   1 回       6,022
  ★2 NORMAL / 放置 /   0% / 1倍 / SSR1枚Lv1       105 pt ×   1 回         105
  ────────────────────────────────────────────────────────────
  合計 7,777,777 pt  （残り 0 pt）
```

ぴったり 0 の候補は「ぴったり」バッジを付ける。近似解は残差を明示する。合計回数が同じ候補が並ぶのは想定内で、「この曲は叩きたくない」といった事情に応じて選べることに意味がある。

### 5.3 永続化

状態は `i7_point_calc_state` として localStorage に保存し、`src/lib/storage.ts` の `STORAGE_KEYS` に追加する（`FooterTools.svelte` のバックアップ対象に含めるため）。

### 5.4 デザイン

- 入力パネル・結果カードともに `surface-card`（不透明）。半透明面に本文テキストを載せない
- 見出しは `text-display`、pt の数値列は `tabular-nums`
- 配色は無彩色（近黒 `#14151A` / 白 / グレー階調）。`indigo` は使わない
- 候補の行はリスト要素なので `backdrop-filter` を使わない

## 6. テスト戦略

### 6.1 ゴールデンテスト（pt 表）

スプレッドシート全 11 シートを手動解析した結果は前述のとおりだが、抽出スクリプトによる自動フィクスチャ化の対象は、gid を取得できる公開 8 シートの pt 表（特効%列 + 弱編成 2 列）のみである。`tests/fixtures/point-calc-golden.json` に抽出する。

```jsonc
{
  "source": "1hVilwOeLHvrkqburgdbAypQSj1p58VFZYwBjKRais08",
  "extractedAt": "2026-08-06",
  "cells": [
    { "sheet": "バディナナ用", "cell": "F16", "stars": 2, "difficulty": "EASY",
      "playMode": "FC", "bonusPct": 0, "unit": "max", "multiplier": 1, "value": 1386, "expected": 1386 },
    { "sheet": "バディナナ用", "cell": "C12", "stars": 1, "difficulty": "EASY",
      "playMode": "放置", "bonusPct": 0, "unit": "weak", "multiplier": 1, "value": 79, "expected": 79 }
    // … 4,423 件
  ],
  "knownSheetErrors": [
    { "sheet": "バディナナ用", "cell": "AH24", "stars": 4, "difficulty": "EASY",
      "playMode": "PC", "bonusPct": 180, "unit": "max", "multiplier": 1, "value": 2729,
      "reason": "★4 EASY PC 180%。セルの式が 8188/3 = 2729.33… で非整数。正しくは 8118/3 = 2706" }
    // … 26 件
  ]
}
```

テストは `cells` 全件で `livePoint` の出力が `expected`（`value` と同値）に一致することを検証する。`knownSheetErrors` は「ツールの出力（`livePoint`）が `value`（シート側の誤値）とは一致しない」ことを検証し、除外が意図的であることを固定する。

抽出スクリプトは `scripts/extract-point-calc-golden.mjs` として置き、シートが更新されたら再生成できるようにする。

### 6.2 ソルバーのテスト

- スプレッドシート上部の `差異 − (セル×回数 + …) = 0` 形式の実例を複数ケース用意し、ソルバーが返す組合せの合計が差異と一致することを検証する
- 性質テスト: 返された全候補について「内訳の `pt × 回数` の総和 + 残差 = 差異」が常に成り立つこと
- 到達不能ケース: 候補を「100 の倍数のみ」に絞った上で差異 `7` を与え、`0` ではなく残差付きの近似解が返ること
- ランキング順序: 合計回数の昇順になっていること

### 6.3 E2E

`tests/point-calc.test.ts` で、目標 pt / 現在 pt を入力して候補が表示されること、特効%チップの編集が結果に反映されること、リロード後に入力が復元されることを確認する。

## 7. 検討したが採用しなかった案

| 案 | 不採用の理由 |
|----|-------------|
| 表の再現ビューア（セルをクリックして回数を積む） | スプレッドシートの操作感をそのまま移すだけで、試行錯誤の手間が残る。自動探索の方が価値が高い |
| 上限回数を決めた DFS 全探索 | 差異が大きいと解なしになり、結局メイン周回の概念が必要になる |
| 差異全体を coin-change DP | `7.7M × 900` ≈ 70 億ステップ。Web Worker でも数十秒かかり非現実的 |
| pt 表を JSON として丸ごと持ち込む | イベントごとに手でメンテが必要。式で再現できることが検証できたため不要 |
| pt 表を Google Spreadsheet の新シートに置いて GViz 取得 | 同上。加えてシート側の入力ミス 27 件をそのまま取り込んでしまう |
| 所持衣装連動で実際に組める特効%に絞る | MVP のスコープ外。特効%を手編集できれば当面代替できる |
