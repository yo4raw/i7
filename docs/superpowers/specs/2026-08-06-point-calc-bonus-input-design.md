# ポイント芸計算ツール 特効入力の枚数化 設計

- 日付: 2026-08-06
- 対象: `/point-calc/`（[初版設計](2026-08-06-point-calc-design.md) / [ADR 0049](../../adr/0049-point-calc-tool.md)）
- 関連 ADR: [0050](../../adr/0050-point-calc-bonus-count-input.md)

## 1. 背景

初版の特効入力は「特効%のチップ集合」だった。既定値は開催中のポイント系イベントの `gpt_up` から達成可能段階を全列挙して生成し、ユーザーはチップを削除・追加して調整する形になっていた。

これが 2 つの問題を起こしていた。

1. **既定値が意図しないイベントから作られる。** `pickDefaultEvent` は開催中のイベントを優先し、無ければ開始日が最も新しいものを選ぶ。ところがイベント ID 237「共鳴のアルカソング」は `end_date` が `0000-00-00`（終了日未定）で、`isEventLive` の日付パースが `NaN` になり開催中と判定されない。結果、終了済み扱いのまま「最も新しいイベント」として選ばれ続けていた。
2. **チップが多すぎて意味が読み取れない。** 上記イベントの `gpt_up` は 50/20/0 で、6 スロット分の達成可能段階を全列挙すると 25 個のチップが並ぶ。「0 / 20 / 40 / 50 / 60 / 70 / …」という羅列は、自分の編成と対応づけられない。

ユーザーからの指摘は「特効がへんなことになっている」であり、要望は「% ではなく金特効 X 枚・銀特効 X 枚・銅特効 X 枚として X を入力する形にしてほしい」だった。

## 2. 用語

サイト既存表記に合わせて「特**効**」を用いる（`src/components/CardList.svelte` のフィルタ、`src/lib/data/eventBonusTiers.ts` の `optionLabel`、イベントページ等がすべて「特効」）。

| 本設計での表記 | 参照スプレッドシートの表記 | データ上のキー |
|---|---|---|
| 金特効 | 特効 | `special1` / `gold` |
| 銀特効 | 準特効 | `special2` / `silver` |
| 銅特効 | 準々特効 | `special3` / `bronze` |

## 3. 決定

### 3.1 入力を「上昇率 × 使える枚数」の 6 入力にする

特効%チップを廃し、次の数値入力に置き換える。

```
特効の上昇率        金特効 [ 50 ] %   銀特効 [ 20 ] %   銅特効 [  5 ] %
使える特効衣装      金特効 [  6 ] 枚  銀特効 [  0 ] 枚  銅特効 [  0 ] 枚
                    ※ フレンドから借りる分を含めた枚数（各 0〜6）

→ 使う特効%: 0 / 50 / 100 / 150 / 200 / 250 / 300%（7 段階）
```

- 枚数は**フレンド枠を含めた 6 枠分**を 1 つの数として入れる。フレンドを別入力に分けない（pt 計算上は合計しか効かないため、入力を増やす意味がない）。
- 最終行の導出結果は**読み取り専用**で表示する。何が候補になっているかが見えないと結果を検算できないため残すが、直接編集はできない。段階数が多くなる組合せ（例: 上昇率 50/20/5・枚数 6/6/6 なら 49 段階）でも省略せず全部出す。読み取り専用なので削除操作の煩雑さはなく、多いこと自体がユーザー自身の入力の結果として読める。

### 3.2 枚数は「使える枚数」であって「確定した編成」ではない

入力した枚数は上限として扱い、**その範囲で組めるすべての特効%を候補にする**。「金 2 枚持っているが 1 枚だけ入れて叩く」というポイント芸の定石を自動的に含められる。確定編成として 1 つの特効%に固定する案は、候補 pt 値が激減してぴったりにできない差異が増えるため採らない。

### 3.3 上昇率は直接入力とし、イベント DB への依存をなくす

金・銀・銅の上昇率はユーザーが手で入れる。イベント選択ドロップダウンを置く案もあったが、直接入力なら未登録のイベントでも使え、1 節の問題 1 が根本からなくなる。

これにより `/point-calc/` はイベントデータを一切参照しなくなる。

### 3.4 弱編成の扱いは変更しない

微調整用の弱編成（`ssr1` = SSR1枚Lv1、`weak` = SR以下Lv1）は、現状どおりすべての特効%と組み合わせる。参照スプレッドシートでは弱編成の列が特効 0% 相当の位置にあるが、フレンドから特効を借りれば弱編成でも特効は乗るため、現状の扱いを維持する方が候補が減らない。本変更のスコープ外とする。

## 4. 実装

### 4.1 `src/lib/pointCalc/bonusPresets.ts`（作り直し）

```ts
/** 各ティアの上昇率（%） */
export interface BonusRates { gold: number; silver: number; bronze: number }

/** 使える特効衣装の枚数（フレンド枠を含む） */
export interface BonusCounts { gold: number; silver: number; bronze: number }

export function achievableBonusPcts(
  rates: BonusRates,
  counts: BonusCounts,
  slots?: number,
): number[];
```

`g ≤ counts.gold` / `s ≤ counts.silver` / `b ≤ counts.bronze` かつ `g + s + b ≤ slots`（既定 `DECK_SLOTS` = 6）を満たす全組合せについて `g × rates.gold + s × rates.silver + b × rates.bronze` を求め、重複を除いて昇順で返す。`0` は必ず含む。上昇率が 0 のティアは値に寄与しないので、枚数を変えても新しい値を生まない。

上昇率・枚数とも、この関数の中で `Math.max(0, Math.trunc(...))` により非負整数へ正規化する。UI 側でも入力時にクランプするが、関数単体で呼んでも壊れないようにしておく（単体テストが直接呼ぶため）。

### 4.2 削除するもの

上昇率を手入力にしたことで不要になる。

| 対象 | 場所 |
|---|---|
| `PointEventSummary` / `isPointEvent` / `pickDefaultEvent` / `defaultBonusPcts` | `src/lib/pointCalc/bonusPresets.ts` |
| `FALLBACK_BONUS_PCTS` / `MAX_BONUS_PCT` | `src/lib/pointCalc/constants.ts`（チップ追加バリデーション専用だった） |
| `fetchEventsCsv` 呼び出しと `events` props | `src/pages/point-calc/index.astro` |

`DECK_SLOTS` は残す（`achievableBonusPcts` の既定スロット数として使う）。

### 4.3 変更しないもの

`engine.ts` / `candidates.ts` / `solver.ts` と、ゴールデンフィクスチャおよびそのテストは無変更。特効%が「どこから来るか」だけが変わり、pt の計算方法とソルバーは影響を受けない。

### 4.4 `src/components/PointCalc.svelte`

- 特効%チップの追加・削除・「既定に戻す」UI を削除
- 上昇率 3 入力（`bonus-rate-gold` / `-silver` / `-bronze`）と枚数 3 入力（`bonus-count-gold` / `-silver` / `-bronze`）を追加
- 導出結果を読み取り専用で表示（`data-testid="derived-bonus-pcts"`）
- `buildCandidates` に渡す `bonusPcts` は `achievableBonusPcts(bonusRates, bonusCounts)` の結果に差し替え
- `events` props を削除

入力範囲は上昇率 0〜100（整数）、枚数 0〜6（整数）。範囲外は入力時にクランプする。

### 4.5 永続化

`i7_point_calc_state` の `bonusPcts` を `bonusRates` / `bonusCounts` に差し替える。本機能は PR #404 が未マージで**まだリリースされていない**ため、旧キーのマイグレーションは行わない（旧 `bonusPcts` が保存されていても無視して既定値を使う）。`STORAGE_KEYS` への変更はない。

### 4.6 既定値

| 項目 | 既定値 | 理由 |
|---|---|---|
| 上昇率 | 金 50 / 銀 20 / 銅 5 | 吉兆の調べ・BUDDY NIGHT NARRATIVE 系で最頻の刻み |
| 枚数 | 金 6 / 銀 0 / 銅 0 | 0〜300% の 50 刻み 7 段階になる。初回表示が読みやすく、手を入れやすい |

## 5. テスト

- `tests/unit/pointCalc/bonusPresets.test.ts` を新 API 向けに書き直す。検証項目: 枚数上限が効く / スロット上限 6 が効く / `0` を含む / 昇順かつ重複なし / 上昇率 0 のティアが値を増やさない / 全枚数 0 なら `[0]` のみ / 負値・非整数の正規化
- `tests/point-calc.test.ts`（E2E）のチップ操作テストを、上昇率・枚数入力の操作と導出結果の反映を確認するテストに差し替える
- `engine` / `candidates` / `solver` / `golden` の各テストは無変更で通ること
- カバレッジゲート（`src/lib/**` 95%）を維持すること

## 6. 検討したが採用しなかった案

| 案 | 不採用の理由 |
|---|---|
| 枚数を「確定した編成」として扱い特効%を 1 つに固定する | 入力は分かりやすいが候補 pt 値が激減し、ぴったりにできない差異が増える。「一部だけ外して叩く」というポイント芸の定石も表現できない |
| フレンド枠を別入力に分ける | pt 計算上は合計しか効かないため、入力欄を 1 つ増やす価値がない |
| 上昇率をイベント選択ドロップダウンから取る | 衣装比較・編成組合計算と同じパターンで既存実装に沿うが、イベント DB への依存が残り、`end_date` が `0000-00-00` のような欠損データに再び影響される。直接入力なら未登録イベントでも使える |
| イベント選択 + 手動上書きの併用 | 入力項目が増えて画面が負ける割に、直接入力に対する利得が小さい |
| 弱編成を特効 0% に固定する | 参照スプレッドシートの見た目には近いが、フレンドから特効を借りれば弱編成でも特効は乗る。候補が減ってぴったりにしづらくなる |
