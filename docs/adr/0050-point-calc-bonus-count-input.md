# 0050 ポイント芸計算ツールの特効入力を「上昇率 × 使える枚数」にする

- ステータス: 承認
- 日付: 2026-08-06

## 文脈

ADR 0049 で追加したポイント芸計算ツール (`/point-calc/`) の特効入力は「特効%のチップ集合」だった。既定値は開催中のポイント系イベントの `gpt_up` から達成可能段階を全列挙して生成していた。

これが 2 つの問題を起こした。

1. **既定値が意図しないイベントから作られる。** `pickDefaultEvent` は開催中を優先し、無ければ開始日が最も新しいものを選ぶ。イベント ID 237「共鳴のアルカソング」は `end_date` が `0000-00-00`（終了日未定）で `isEventLive` の日付パースが `NaN` になり開催中と判定されないため、終了済み扱いのまま「最も新しいイベント」として選ばれ続けていた。
2. **チップが多すぎて意味が読み取れない。** 上記イベントの `gpt_up` は 50/20/0 で、達成可能段階を全列挙すると 25 個のチップが並ぶ。ユーザーが自分の編成と対応づけられない。

ユーザーからの指摘は「特効がへんなことになっている」で、要望は「% ではなく金特効 X 枚・銀特効 X 枚・銅特効 X 枚として X を入力する形にしてほしい」だった。

## 決定

1. **特効入力を「上昇率 3 入力 × 使える枚数 3 入力」に置き換える。** 特効%チップの追加・削除 UI は廃止し、導出された特効%の一覧は読み取り専用で表示する（結果を検算できるようにするため）。

2. **表記は 金特効 / 銀特効 / 銅特効 に統一する。** 参照スプレッドシートの「特効 / 準特効 / 準々特効」ではなく、サイト既存表記（`CardList.svelte` のフィルタ、`EVENT_BONUS_TIERS` の `optionLabel`、イベントページ）に合わせる。データ上の `special1` / `special2` / `special3` = `gold` / `silver` / `bronze` に対応する。「特攻」ではなく「特効」と書く。

3. **枚数はフレンド枠を含めた 6 枠分を 1 つの数で入れる。** フレンドを別入力に分けない。pt 計算上は各ティアの合計枚数しか効かないため、入力欄を増やす価値がない。

4. **枚数は「使える枚数」であって「確定した編成」ではない。** 入力値を上限として、その範囲で組めるすべての特効%を候補にする。「金 2 枚持っているが 1 枚だけ入れて叩く」というポイント芸の定石を自動的に含められる。

5. **上昇率は直接入力とし、イベント DB への依存をなくす。** これにより `/point-calc/` はイベントデータを一切参照しなくなり、上記の問題 1 が根本からなくなる。`PointEventSummary` / `isPointEvent` / `pickDefaultEvent` / `defaultBonusPcts` と、`FALLBACK_BONUS_PCTS` / `MAX_BONUS_PCT` を削除する。

6. **既定値は 上昇率 金 50 / 銀 20 / 銅 5、枚数 金 6 / 銀 0 / 銅 0 とする。** 上昇率は吉兆の調べ・BUDDY NIGHT NARRATIVE 系で最頻の刻み。枚数は 0〜300% の 50 刻み 7 段階になり、初回表示が読みやすい。

7. **弱編成（SSR1枚Lv1 / SR以下Lv1）の扱いは変更しない。** 現状どおりすべての特効%と組み合わせる。フレンドから特効を借りれば弱編成でも特効は乗るため、0% に固定すると候補が不必要に減る。

8. **`engine.ts` / `candidates.ts` / `solver.ts` とゴールデンテストは無変更。** 特効%が「どこから来るか」だけが変わり、pt の計算方法とソルバーは影響を受けない。

## 検討した代替案

- **枚数を「確定した編成」として扱い特効%を 1 つに固定する**: 入力は最も分かりやすいが、候補 pt 値が激減してぴったりにできない差異が増える。「一部だけ外して叩く」定石も表現できない。
- **フレンド枠を別入力に分ける**: pt 計算上は合計しか効かないため、入力欄を 1 つ増やす価値がない。
- **上昇率をイベント選択ドロップダウンから取る**: 衣装比較 (`i7_compare_event_id`) や編成組合計算 (`i7_max_finder_event_id`) と同じパターンで既存実装には沿うが、イベント DB への依存が残り、`end_date` が `0000-00-00` のような欠損データに再び影響される。直接入力なら未登録のイベントでも使える。
- **イベント選択 + 手動上書きの併用**: 入力項目が増えて画面が負ける割に、直接入力に対する利得が小さい。
- **弱編成を特効 0% に固定する**: 参照スプレッドシートの見た目には近いが、フレンドから特効を借りれば弱編成でも特効は乗る。候補が減ってぴったりにしづらくなる。

## 影響

- `src/lib/pointCalc/bonusPresets.ts` を作り直し、`achievableBonusPcts(rates, counts, slots?)` のみを公開する。
- `src/lib/pointCalc/constants.ts` から `FALLBACK_BONUS_PCTS` / `MAX_BONUS_PCT` を削除（`DECK_SLOTS` は残す）。
- `src/pages/point-calc/index.astro` から `fetchEventsCsv` 呼び出しと `events` props を削除。
- `src/components/PointCalc.svelte` の特効入力 UI を差し替え、`i7_point_calc_state` の `bonusPcts` を `bonusRates` / `bonusCounts` に変更。PR #404 が未マージでまだリリースされていないため、旧キーのマイグレーションは行わない。
- 詳細設計は `docs/superpowers/specs/2026-08-06-point-calc-bonus-input-design.md` を参照。
