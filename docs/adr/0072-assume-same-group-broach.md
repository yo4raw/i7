# 0072 グループ限定の固有ブローチを衣装比較・編成組合計算では発動扱いで加算する

- ステータス: 承認
- 日付: 2026-09-03

## 文脈

固有ブローチの種類4（グループ限定）は、センターとメンバー4枚（自枠5枚）がすべて同一グループのときだけ発動する。`resolveDeckBroachs()` の `hasNoOtherGroup()` がこれを判定している。

この判定はスコア計算では正しい。一方で、ベストケースを比べる 2 つの画面では扱いが揃っていなかった。

- 衣装比較は 1 枚デッキ `[card, null×5]` で評価するため、他グループの衣装が同居せず、種類4は結果的に常に成立していた。意図した仕様ではなく、評価デッキの形から偶然そうなっていただけである。種類7（全属性編成）には同じ目的で `assumeAllAttributes` オプションが明示的に用意されている。
- 編成組合計算は実デッキで評価するため、混成の編成では種類4が発動せず加算されない。探索候補はイベントの特効 UR に限られ、特効はグループをまたぐことが多いので、グループ限定ブローチを持つ衣装は事実上その分を評価されないまま順位が決まっていた。

さらに、種類4のブローチを持つ衣装は「5th / 7th / 10th Anniversary」のグループ別衣装に限られるが、これらはカードデータの `groupname` が空である。`hasNoOtherGroup()` はデッキの各衣装の `groupname` をブローチ指定グループと突き合わせるため、この衣装自身が条件を満たさない。結果として、同グループで揃えた編成であっても種類4は一度も発動していなかった。

## 決定

### 1. 両画面でグループ限定ブローチを発動扱いで加算する

`ResolveBroachOptions` に `assumeSameGroup` を追加し、種類4の判定を `broach.group !== null && (assumeSameGroup || hasNoOtherGroup(deck, broach.group))` とする。既定は false なので、スコア計算の挙動は変わらない。

衣装比較（`cardStrength.ts`）は `assumeAllAttributes` と併せて明示的に渡す。挙動は変わらないが、成立していた理由がデッキの形の偶然ではなく意図であることをコードに残す。

編成組合計算（`maxScoreFinder.ts` の `evaluateDeck`）は `FINDER_BROACH_OPTIONS` として渡す。`computeTeam()` に `broachOptions` 引数を足して `resolveDeckBroachs()` へ透過させる。

この変更は探索スコアそのものを動かすため、最良編成のランキングも変わる。グループ限定ブローチを持つ衣装が、実際には発動しない混成の編成でも上位に来る。それでもこちらを採る。両画面はいずれも「ベストケースで衣装の強さを比べる」ための道具であり、発動しうる効果を評価から落とすほうが比較の道具としては誤りが大きい。加算しない場合、利用者は「グループを揃えればこの衣装がどれだけ伸びるか」をこのツールからは知りようがない。

### 2. 誤解を防ぐ注意書きを画面と解説の両方に置く

加算は実際には成立しない前提の上に立つため、数値だけを見せると達成不能なスコアを提示することになる。次の 4 箇所に注記を置く。

- 編成組合計算の結果「衣装詳細」: 最良編成に発動扱いの種類4が含まれるときだけ、加算している旨と実際の発動条件を出す。常時表示にはしない（該当しない編成では雑音になる）
- 編成組合計算の結果のブローチ表示: 種類4のチップに「（同グループ編成が前提）」を併記する。表示側も同じオプションで解決し、「スコアには乗っているのにチップは条件未達」という食い違いを作らない
- 衣装比較の一覧下: グループ限定・全属性編成を条件を満たしたものとして加算している旨を常時表示する。衣装ごとの前提は従来どおり詳細パネルの「ブローチ前提」欄に出る
- 両ページの `ToolGuide`（ADR 0058）: 解説の notes と、編成組合計算の FAQ「スコア計算ページの結果と数字が違う」に、この差分の理由を追記する

## 検討した代替案

### ランキングは現状のまま、表示のみ「同グループ編成なら +X」と併記する

探索スコアは実際に達成可能な値のままになるため、数値の正確さは保たれる。却下した。編成組合計算の出力は「どの 6 枚を組むか」の意思決定に使われるので、順位に反映されない情報は実質的に読まれない。グループを揃える選択肢そのものが候補から消える。

### 設定トグルで切り替える

既定オフで現状維持、オンで加算。却下した。この前提は 2 つの画面に共通する「ベストケースで比べる」という性格から来るもので、利用者ごとに切り替える種類の設定ではない。トグルが増えるぶん、どちらの数値を見ているのかがかえって分かりにくくなる。
