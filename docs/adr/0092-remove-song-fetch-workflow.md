# 0092: 楽曲画像の cron ワークフローを削除し、ローカルスクリプトによる手動取り込みに一本化する

- 日付: 2026-09-19
- ステータス: 承認

## 背景

楽曲ジャケット画像は `fetch-new-songs.yml` が IDOLiSH7 Wiki（Miraheze）から定期取得していたが、2026-09-04 以降 Miraheze が GitHub Actions の IP 帯を 403 で弾いており、すべての run が失敗している。ADR 0076 で頻度を 6 時間おきに減らし、ADR 0088 で同じ取り込みをローカルで行う `npm run fetch-songs` を追加したうえで「cron はブロックが解ければ自動復旧するので残す」としていた。

その後も 2 週間ブロック解除の兆しはなく、新曲の画像は ADR 0088 のローカル実行だけで取り込んでいる。失敗し続ける run は Actions の履歴を埋め、失敗通知が来るたびに「既知の 403」と確認する手間だけが残っていた。

## 決定

**`.github/workflows/fetch-new-songs.yml` を削除する。** 楽曲ジャケット画像の取り込みは `npm run fetch-songs`（`scripts/fetch-song-images-local.sh` → `scripts/fetch-song-images.mjs`）のローカル実行に一本化する。

- クローラー本体 `scripts/fetch-song-images.mjs` と `scripts/lib/util.mjs` の `fetchRetry` は残す（ローカル実行で使う）
- 新曲が追加され `src/data/event-songs.json` にイベント対象楽曲を登録するときに、あわせて `npm run fetch-songs` を実行する運用は ADR 0088 のまま
- 衣装画像・イベント DB の cron 2 本（`fetch-new-cards.yml` / `fetch-event-db.yml`）は変更しない。ゲームサーバー側はブロックされていない
- ブロックが解けたことが分かり、再び自動化したくなったら、削除したワークフローを git 履歴から復元する（本 ADR を `破棄` に更新する）
- ADR 0076 は対象のワークフローが無くなるため `破棄` にする。ADR 0088 は「cron を残す」の部分だけが覆り、ローカルスクリプトの決定は有効

## 検討した代替案

- **cron を残してブロック解除を待つ（現状維持）** — 2 週間で解除の兆しがなく、失敗通知の確認コストだけが積み上がる。復元は git から 1 コマンドでできるので、残しておく利点が小さい
- **schedule だけ外して `workflow_dispatch` 専用にする** — Actions の IP 帯からは手動実行しても同じく 403 になるため、実行しても成功しない。動かないボタンを残すのは誤解のもと
- **セルフホストランナーや外部プロキシ経由で取得する** — 無料運用のサイトに常駐インフラや外部サービスを足すことになる。新曲は月に数曲で、ローカル実行の手間はイベント対象楽曲の登録作業と同じタイミングで済む
- **Miraheze のボットアカウント認証で回避する** — ADR 0076 で見送り済み。IP ブロックが認証で回避できるか未検証で、資格情報の管理も増える
