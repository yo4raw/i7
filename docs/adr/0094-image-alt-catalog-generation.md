# 0094: 画像 alt を「識別情報 + ビジュアル描写」のカタログとして生成する

- 日付: 2026-09-26
- ステータス: 提案

## 背景

`public/assets/` には 6,420 枚の画像がある（カード本体 2,893 / カードサムネ 3,376 / 楽曲ジャケット 151）。しかし `src/` の `<img>` 21 箇所は `alt={card.cardname}` / `alt={song.song_name}` を機械的に埋めており、スクリーンリーダーには「Photo Collection -潤-」のような名称だけが届く。カードは絵が主役のメディアなので、名称だけでは絵の中に何があるかが伝わらない。

一方で、alt を単に長くするのは正しいとも限らない。絵を explained する文章で固めた alt は、隣に同じカード名を本文として表示している一覧では読み上げが二重になり、一覧の走査を遅らせてしまう。

## 決定

**alt を「識別情報 + ビジュアル描写」という 1 本の文として、データカタログとして生成する。**

- 識別情報（キャラクター名・カード名・レアリティ・属性・楽曲名）は **シートの値を正とする**。sub-agent には書かせない
- ビジュアル描写（絵の中の人物・服装・ポーズ・背景）は **sub-agent が画像を見て書く**
- 二者は **決定論スクリプトで合成する**。alt 文字列そのものではなく描写だけを生成物に保存するので、模板を修正しても 3,527 件を書き直す必要がない
- 対象は 6,420 枚ではなく **3,527 件**。`cards/<id>` と `th_cards/<id>` は同一作品の表裏なので alt を共有する
- 生成と利用を分離する。**今回はカタログと合成ロジックの実装までとし、アプリへの結線は別タスクとする**

## 検討した代替案

- **ビジュアル描写だけを書く** — シートに対応行が無いカード 505 枚では名前が无论如何入らない。識別情報はシートに値がある以上、そちらを使うほうが確実
- **alt を現状の `cardname` のままにする** — 名前としては正しいが、絵が主役のメディアとして情報不足
- **生成物を alt 完成形の JSON にする** — 配布する系列 Groups はないが、書式を変えたいたびに 3,527 件を再生成する必要がある
- **sub-agent を使わず 1 枚ずつ手書きする** — 元画像（800x1200）のままだと画像トークンが約 3.8M。512x768 に縮小してから読ませれば約 1.6M に収まる
- **sub-agent の戻り値として alt を受け取る** — 3,527 件分がそのまま実行者のコンテキストを圧迫する。ファイル（JSONL）経由に限定した
- **1 枚ずつ別の sub-agent に渡す** — 3,527 本になり運用が破綻する。1 バッチ 100 枚なら 36 本で足りる
- **6,420 枚すべてを別々に記述させる** — 同じ絵の表裏に対し 2 回書かせることになり、無駄かつalt が食い違う
