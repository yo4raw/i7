# 0068 同一カテゴリ内の同名曲を 1 行に畳む

- ステータス: 承認
- 日付: 2026-09-02

## 文脈

`/songs/?group=ŹOOĻ` に「Ache」が 2 行表示されるという報告があった。GViz 経由で取得しているマスターデータ（スプレッドシート GID 1083871743）の生データを検証したところ、原因はサイトのコードではなくデータ側にあった。

| ID | song_type | difficulty | ノーツ | 秒 | updated_at |
| -- | --------- | ---------- | ------ | -- | ---------- |
| 42 | イベント楽曲 | EXPERT+ | 315 | 94 | 2023-08-31 |
| 43 | 通常楽曲 | EXPERT | 282 | 94 | 2024-08-30 |

有効な 149 曲を全数調べると、ID 43 は 3 つの観点すべてで唯一の外れ値だった。

- `difficulty`: EXPERT+ が 148 件、EXPERT が 1 件（ID 43 のみ）
- `song_type`: イベント楽曲が 148 件、通常楽曲が 1 件（ID 43 のみ）
- カテゴリ + 曲名の重複: Ache の 1 組のみ（曲名だけで見ても他に重複はない）

つまりこのシートは **「1 曲 = 1 行（イベント楽曲の EXPERT+ 譜面）」** という慣習で運用されており、ID 43 だけがそこから外れている。2023 年のイベント時に ID 42 が登録され、2024 年に通常楽曲へ移った際、既存行に気づかず ID 43 として再登録されたと見られる。

サイト側は有効な行を忠実に描画しているだけで、`SongList` にも `filterValidSongs` にも欠陥はない。ただし利用者から見れば、一覧にも曲選択ドロップダウンにも同名の行が 2 つ並ぶ状態であり、どちらを選べばよいか判断できない。

この種の登録ミスは 1 年越しで起きており、149 曲中 1 件という頻度では人の目で気づきにくい。データを直すだけでは再発時にまた同じ状態が本番へ出る。

## 決定

**マスターデータの ID 43 を削除する。あわせて、同一カテゴリ内で曲名が重複した場合は難易度の高い行だけを残すよう `filterValidSongs` に重複排除を入れる。**

データ側の修正が根本原因への対処で、コード側の重複排除は再発に対する防御である。どちらか片方では不十分と判断した。

### 重複排除の規則

`src/lib/data/fetchSongsJson.ts` に `dedupeSameSong()` を追加し、`filterValidSongs()` から呼ぶ。

- キーは **カテゴリ + 曲名の完全一致**。表記ゆれの正規化（大小文字・空白の吸収）はしない。別の曲を誤って畳むリスクのほうが、表記ゆれを取りこぼすリスクより高いため
- 重複したら **難易度が高い行を残す**（`EXPERT+` > `EXPERT` > `HARD` > `NORMAL` > `EASY`、未知・未入力は最下位）。シートの慣習が EXPERT+ である以上、EXPERT+ を正とする
- 難易度が同順位なら **先に現れた行を残す**（シートの並び順に従う）
- 重複がなければ **並び順を変えない**

`filterValidSongs` は一覧・曲選択・スコア計算・編成組合計算・衣装比較・保存デッキ・楽曲詳細のすべてが通る唯一の入口なので、ここに入れればサイト全体へ一度に効く。

### カテゴリ一致を条件にする理由

別ユニットが同名曲をカバーしている場合、カテゴリが異なれば別の曲として残す必要がある。現データにそうした例はないが、曲名だけをキーにすると将来そうした曲が入ったときに片方が消える。

## 検討した代替案

- **スプレッドシートの ID 43 を削除するだけ**: 根本原因は消えるが、同じ登録ミスが再発したときに再び本番へ出る。1 年越しで起きた種類のミスであり、次も気づかない可能性が高い
- **コード側の重複排除だけ入れる**: 表示は直るが、データには誤った行が残り続ける。他のツールやシートの閲覧者から見た不整合は解消しない
- **`difficulty !== 'EXPERT+'` の行を捨てる**: 実装は単純だが、将来 EXPERT+ 譜面を持たない曲が追加されたときにその曲ごと消える。重複していない行には触れない設計にすべき
- **2 行のまま残し、一覧で見分けやすく表示する**: Ache の EXPERT+ と EXPERT は実際に別譜面なので情報としては正しい。ただしこのサイトはイベントのスコア計算が主目的で、譜面の選択という概念を持たない。曲選択ドロップダウンに同名が 2 つ並ぶ状態も残るため採らなかった

## 影響

- `src/lib/data/fetchSongsJson.ts`: `DIFFICULTY_RANK` / `difficultyRank()` / `dedupeSameSong()` を追加し、`filterValidSongs()` から呼ぶ
- `tests/unit/filterValidSongs.test.ts`: 新規。絞り込みと重複排除の規則を固定
- スプレッドシート: ID 43 の行を削除する（リポジトリ外の作業）
- ID 43 の削除により楽曲数は 149 → 148 になる。`/songs/43/` は生成されなくなる
- 保存済みのスコア計算状態が ID 43 を指していた場合、`ScoreCalc.applyState()` は該当曲が見つからなければ選択を復元しないだけなので、エラーにはならない
