# 0081: イベント対象楽曲をイベント単位で管理し、イベント詳細に表示する

- 日付: 2026-09-08
- ステータス: 承認

## 背景

イベント詳細ページ (`/events/{id}/`) に「そのイベントの対象楽曲」が表示されていなかった。

対象楽曲のデータは `src/data/event-songs.json` の `eventSongIds` にあるが、これは ADR 0021 で導入した**グローバルな 1 配列**で、「曲選択ドロップダウンの先頭にピン留めする曲」を表す。どのイベントの曲なのかを持っていない。ADR 0074 はこの制約を理由に、衣装比較の共有ページをイベント配下 (`/events/{id}/share/songs/`) へ置く案を見送っている（過去イベントのページが現行イベントの曲を表示してしまうため）。

イベント DB (`public/events/events.csv`) にも楽曲の列はないため、ゲーム側から自動で取得できるデータもない。

## 決定

`event-songs.json` を**イベント ID をキーにしたマップ**に変え、イベント詳細ページに「対象楽曲」セクションを追加する。

- データ構造: `eventSongIds: number[]` → `currentEventId: number` + `byEvent: { [eventId]: number[] }`（配列順が表示順／先頭が既定選択）
- `getEventSongIds(eventId?)` は `byEvent[eventId]` を返す。**引数省略時は `currentEventId`** のイベントを返すため、`SongSelect` の「イベント対象楽曲」グループと `firstEventSongId()` の既定選択は従来どおり動く
- イベント詳細は `getStaticPaths()` で楽曲マスターを取得し、`byEvent[event.id]` の曲をジャケット付きグリッドで静的にレンダリングする（クライアント JS なし）。未登録のイベントはセクションごと出さない
- 登録は引き続き手作業。新イベントの曲を追加するときは `byEvent` に行を足し、`currentEventId` を同じ ID へ更新する

過去イベントの対象楽曲は遡って登録していないため、当面は `currentEventId` のイベントだけにセクションが出る。誤った曲を出すよりは出さないほうがよい、という判断。

## 検討した代替案

- **グローバルな `eventSongIds` のまま全イベントで表示** — 過去イベントのページに現行イベントの曲が並ぶ。ADR 0074 が見送った問題そのもので不採用
- **開催中のイベントにだけグローバル配列を出す** — 「開催中」の判定はクライアント側（`EventStatusBadge`）で行うため島が必要になり、イベント終了後は誰にも出なくなる。データを正しい形にするほうが安い
- **`byEvent` のキー最大値を現行イベントとみなす（`currentEventId` を持たない）** — 次イベントの曲を先行登録した瞬間に曲選択の既定が切り替わってしまうため不採用
- **events.csv に楽曲列を足す** — CSV はゲームサーバーから cron で取得しているもので、こちらから列を足せない
