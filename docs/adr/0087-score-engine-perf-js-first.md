# 0087: 計算速度の改善は Rust/wasm ではなく JS 側のアルゴリズム改善と Worker 分散で行う

- 日付: 2026-09-15
- ステータス: 承認

## 背景

編成組合計算（総当たり探索）は候補 30 枚で 2,000 万件超の編成を評価し、7 並列でも数分かかる。「Rust で書いて wasm にすれば速くなるか」という問いに対し、実測してから判断した。

計測（fixture 楽曲 id 2、UR 30 枚、Node 1 コア）では 1 編成の評価が約 80 µs で、その 7 割を `calcExpectedScore` がノーツ 428 件を毎回なめる素点合計に、2 割を `flattenNotes` によるノーツ配列の再展開に使っていた。どちらもノーツの並び順に依存しない値であり、言語を替えなくても計算量の桁を落とせる。

またスコア計算画面の MC シミュレーション（`runSimulation`）はメインスレッド 1 コアで回っていた（ADR 0056 で Worker 化を見送り）。

## 決定

1. **Rust/wasm 化は採用しない**。
   - 仕様書の floor 位置や丸め規則を二重実装して保守する負担、Card / Song を wasm メモリへ詰め替える転送コスト、GHA への Rust ツールチェーン追加に対し、float と分岐中心のこのコードで見込める伸びは経験的に数倍で、下記のアルゴリズム改善と同じ桁にとどまる
2. **素点合計をノーツ配列ではなく同値バケット（属性 × 種別 × グループ × 除外）の件数表で計算する**。バケット化は配列同一性でキャッシュし、`calcExpectedScore` / `calcMaxScoreBreakdown` / `calcMinScore` の公開シグネチャは変えない
3. **編成組合計算では `flattenNotes` の結果を先頭除外ノーツ数ごとに `SearchContext` で使い回す**。除外は「グループ順に先頭から N 個」なので N だけで一意に決まる
4. **MC シミュレーションは試行回数を Worker に分割して実行し、結果を合成する**（`simulationPool.ts`）。Worker 数は探索と同じ `min(8, hardwareConcurrency − 1)` を上限とし、1 Worker あたり最低 `MC_CHUNK_SIZE` 試行を割り当てる。Worker が使えない環境と、Worker の生成・実行に失敗した場合は、残りの Worker を止めてメインスレッドの `runSimulation` に 1 回だけフォールバックする

計測結果（同条件、`evaluateDeck` 1 コア）:

| | 変更前 | 変更後 |
|---|---|---|
| 算術期待値モード | 12,500 件/秒 | 79,600 件/秒 |
| 理論最大値モード | — | 90,600 件/秒 |

## 検討した代替案

- **Rust/wasm 化** — 上記の理由で見送り。アルゴリズム改善後もなお体感が足りない場合に、改めて ADR を起こして判断する
- **スコア計算関数の引数を FlatNote[] から件数表へ変える** — UI 側の呼び出しをすべて変える必要があり、配列同一性キャッシュで同じ効果が得られるため採らない
- **MC を 1 Worker だけに移す** — UI 応答性は上がるが速度は変わらない。分割合成はスコア配列の連結と加重平均だけで済むため、分散まで行う

## 影響

- スコア計算の値は変わらない（既存の単体テスト・ゴールデンテストで確認）
- MC の乱数列は Worker ごとにシードをずらすため、同じシードでも Worker 数が異なる環境では結果が一致しない。シード指定は単体テスト用途であり、UI では未指定のまま
- ADR 0056 の「MC シミュレーションを Web Worker へ移す（見送り）」は本 ADR で覆す
