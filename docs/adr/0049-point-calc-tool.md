# 0049 ポイント芸計算ツールを式ベースの自動ソルバーとして実装する

- ステータス: 承認
- 日付: 2026-08-06

## 文脈

「ポイント芸」とは、ポイント系イベントの最終獲得ポイントを `7,777,777` のような狙った数字にぴったり揃える遊びである。既存の実現手段は @SachiTgr 氏が公開しているスプレッドシート（`1hVilwOeLHvrkqburgdbAypQSj1p58VFZYwBjKRais08`）で、イベントごとに 1 枚のシートに「1 ライブあたり獲得 pt 表」を持ち、利用者が `= 差異 − (F16*3 + J19*3)` のような式を手で書いて 0 になるまで試行錯誤する運用になっている。

このシートを本サイトに取り込むにあたり、pt 表の数値をどう用意するかが最大の分岐だった。全 11 シート・4,809 セルを解析したところ、**表全体が単純な算術式で再現でき、しかも式はイベント非依存**であることが分かった。シート間の差分は「イベントの特効刻み」と「各★の楽曲名の注記」だけである。

さらに、特効の刻みは `public/events/events.csv` の `special{1,2,3}_gpt_up` と一致することが確認できた（イベント ID 235「BUDDY NIGHT NARRATIVE【BUDDY.3 夢幻】」の `gpt_up: 50/20/5` が `バディナナ用` シートの「特効 50% / 準特効 20% / 準々特効 5%」に対応）。

## 決定

1. **pt 表はデータとして持たず、式で算出する。**

   ```
   獲得pt = floor(グレードpt × (1 + 特効率)) + ユニットボーナス + コンボボーナス
   グレードpt = floor(基礎点[難易度] × 楽曲★倍率 × プレイ係数)
   ```

   | 定数 | 値 |
   |------|-----|
   | 基礎点 | EASY 550 / NORMAL 650 / HARD 750 / EXPERT 1000 |
   | 楽曲★倍率 | ★1 1.20 / ★2 1.23 / ★3 1.25 / ★4 1.28 / ★5 1.30 |
   | プレイ係数 | 放置 0.12 / FC 1.0 / PC 1.0 / オート 1.0（オートのみ★倍率を掛けない） |
   | ユニットボーナス | MAX編成 270 / SSR1枚・特訓なし・Lv1 10 / SR以下・Lv1 0 |
   | コンボボーナス | 放置 0 / オート 300 / FC 440,465,491,555 / PC 465,495,525,600（難易度順） |

   倍率ライブ（2倍 / 3倍）は 1 回分の pt を整数倍する。

2. **計算は整数演算で行う。** `floor(gradePt * (1 + pct/100))` を浮動小数点で書くと `660 × 2.3 = 1517.9999999999998` となり 1pt ずれる。解析時に実際にこの原因で 124 セルが不一致になった。実装は `Math.floor(gradePt * (100 + bonusPct) / 100)` とし、特効率は整数パーセントで保持する。

3. **スプレッドシート側の入力ミスは再現しない。** ただしゴールデンフィクスチャの抽出対象は、全 11 シートのうち公開されている 8 シートのみとする。非公開の隠しシート 3 枚（`アイスタ⑧用` / `マリマリ用` / `Sugao用`）は htmlview のシートスイッチャーから gid を取得する手段がなく、また pt 表の内容は公開シートと重複するため実害がない。抽出スクリプト (`scripts/extract-point-calc-golden.mjs`) の `SHEETS` は公開 8 シートのみを列挙し、合計 4,449 セル中 4,423 セル（99.4%）が式と一致し、残る 26 セルは以下のいずれかで、シート側の誤りと判断した。

   - ★2 NORMAL FC 60% が `2031`（3 シート）— 他 5 シートの同条件は `2013`。桁の入れ替わり
   - ★4 EASY PC 180% が `8188/3 = 2729.33…`（5 シート）— 非整数。正しくは `8118/3 = 2706`
   - Sugao①用 / Sugao②用の 200% 列に 210% の値（18 セル）— 隣の 210% 列と同値

   これらは理由付きでゴールデンフィクスチャの `knownSheetErrors` に記録し、「ツールの出力が正しい値と一致し、かつシートの値とは一致しない」ことをテストで固定する。将来シート側が修正されても差分を追える。

4. **ツールは表のビューアではなく自動ソルバーとする。** 差異を入力すると、ぴったり 0 にできる組合せをライブ回数の少ない順に複数提示する。

5. **探索は「メイン周回 + 端数 DP」の 2 段構えとする。** 差異は数百万に達しうる一方、候補 pt 値の最大は 2 万弱で、差異全体を coin-change DP にかけると 70 億ステップとなり非現実的。メイン周回を `k = floor(差異 / メインpt)` 回と決め、残差 `R` に対してのみ最小回数の unbounded coin change DP を解く。`k` を数回分減らして `R` を振ることで複数候補を得る。

6. **ぴったり 0 にできない場合は近似解を残差付きで返す。** 候補 pt 値の最大公約数の都合で到達できない差異が存在するため、0 にできないものを 0 と言い張らない。

7. **楽曲は★×難易度のみで扱い、楽曲名は扱わない。** pt は★と難易度だけで決まり、楽曲名は影響しないため。

8. **特効%は既定値を自動投入した上でユーザーが編集可能とする。** 開催中のポイント系イベントの `gpt_up` から達成可能段階を生成して既定値とし、チップ形式で追加・削除・数値編集できるようにする。

   > **この決定は [ADR 0050](0050-point-calc-bonus-count-input.md) で置き換えられた。** 終了日が `0000-00-00` のイベントを拾って意図しない既定値が生成される問題と、チップが多すぎて読み取れない問題があったため、「金/銀/銅の上昇率 × 使える枚数」の入力に変更し、イベント DB への依存をなくした。

9. **PC（パーフェクトコンボ）は既定 OFF とする。** PC は実際に出すのが難しく、提示されても実行できない候補になりやすい。プレイ方法はチェックボックスで個別に ON/OFF でき、PC だけ既定を OFF にする。式・ゴールデンテストは PC も含めて実装・検証し、既定値のみで制御する。

## 検討した代替案

- **pt 表を JSON として丸ごと持ち込む**: イベントごとに手でメンテが必要になる。式で完全に再現できることが検証できたため不要。加えてシート側の入力ミス 27 件をそのまま取り込んでしまう。
- **pt 表を Google Spreadsheet の新シートに置いて GViz 経由で取得する**: 本リポジトリの既存パターンには沿うが、上と同じ問題を抱える。式で持つ方がメンテフリーかつ正確。
- **表の再現ビューア（セルをクリックして回数を積み、残差をリアルタイム表示）**: スプレッドシートの操作感をそのまま移すだけで、試行錯誤の手間が残る。自動探索の方が価値が高い。
- **上限回数を決めた DFS 全探索**: 差異が大きいと解なしになり、結局メイン周回の概念が必要になる。
- **差異全体を coin-change DP**: `7.7M × 900` ≈ 70 億ステップ。Web Worker でも数十秒かかる。
- **所持衣装（`i7_card_counts`）と連動して実際に組める特効%に絞る**: 親切だが MVP のスコープ外。特効%を手編集できれば当面代替できる。
- **オートに★倍率を掛ける形で式を統一する**: 見た目は整うが、実データはオートの グレードpt が★に依らず基礎点そのものであることを示している（★1〜★5 の全 EASY でオートの特効係数が一律 550）。データに合わせて例外として扱う。
