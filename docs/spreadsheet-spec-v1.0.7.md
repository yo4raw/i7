`$BB$33`/`$BD$33`/`$BF$33` は行 33 のノーツ得点係数（Shout/Beat/Melody それぞれの単位属性値あたりスコア換算係数と推定されるが、この数式本体は今回のどのレポートでも直接確認できていない。⚠️要確認）。`P4` は `所有カード登録!H4:H1901` の FILTER 由来（カード/スキル領域の境界値）。経路①は単価計算の各段階で `ROUNDDOWN`、経路②は最終 `AC4` でのみ `ROUNDDOWN` するため、同じ入力でも経路①と経路②の数値は一致しない。

### 6-6. スキル計算 (H31-H40) スロット 1 の例

各スロット H-M に対して同形の式が展開される（**行 31・33〜37 は H〜M 全列に存在するが、行 38-40 は H 列のみ数式が確認できる**。§6-2 参照）。以下は H 列（スロット 1）の例。`AM10` がそのスロットの cardID。

#### H31 - スキル種別判定

```
H31 = IFERROR(IFS(
        vlookup(AM10, '衣装データ'!$B:$AR, 17,) = "判定領域を",           "判定領域縮小",
        vlookup(AM10, '衣装データ'!$B:$AR, 17,) = "BAD以上をPerfectに変更", "判定強化",
        vlookup(AM10, '衣装データ'!$B:$AR, 17,) = "MISS以上をPerfectに変更","判定強化",
        vlookup(AM10, '衣装データ'!$B:$AR, 17,) = "MISS→Perfect",         "判定ガード",
        TRUE,                                                            vlookup(AM10, '衣装データ'!$B:$AR, 17,)
      ),)
```

戻り値: `"スコアアップ" / "判定領域縮小" / "判定強化" / "判定ガード"` またはマッチしないスキル種別文字列そのまま（例: `"判定拡大スコアダウン"`）。マッチしない場合は `TRUE, vlookup(...)` のフォールスルーで生値がそのまま入るため、以降の縮小系分岐には一切入らない。

**衣装データの実データ分布**（`衣装データ!R` 列, ap_skill_type, 実測）: スコアアップ(1851)/BAD以上をPerfectに変更(466)/MISS以上をPerfectに変更(32)/MISS→Perfect(152)/判定拡大スコアダウン(32)/**判定領域を**(135)/MISS→GOOD(2)/MISS→Good(1)。合計2671セル。

#### H32 - スキルレベル（ユーザー入力、既定 5）

#### H33 - 発動条件

```
H33 = IFERROR(vlookup(AM10, '衣装データ'!$B:$AR, 18,),)
    // → "Perfect" / "コンボ" / "タイマー"
```

**衣装データ!S 列（ap_skill_req）の実データ分布**: コンボ(919)/タイマー(612)/Perfect(985)/**開始時(155)**。`開始時` は `H33` の内側 `ifs(OR(H33="Perfect",H33="コンボ"),…, H33="タイマー",…)` のどの分岐にも一致しない値であり、少なくとも 20 件は「スコアアップ」等の主要種別に紐付く「開始時」条件が実在すると推定される（`衣装データ!R` の 135 件 < `衣装データ!S` の 155 件から算術的に導かれる）。該当カードが `所有カード登録` に登録されると `H39`/`AD4` は `#N/A` となり、`RANK` 計算まで壊れるリスクがある（⚠️要確認、`score-up.md`）。

#### H34-H37 - スキルパラメータ（レベル別、丸めなし）

```
H34 = vlookup(AM10, '衣装データ'!$B:$AR, 16 + (skillLevel × 4),)    // count
H35 = vlookup(AM10, '衣装データ'!$B:$AR, 17 + (skillLevel × 4),)    // per (%)
H36 = vlookup(AM10, '衣装データ'!$B:$AR, 18 + (skillLevel × 4),)    // value (秒 or スコア)
H37 = vlookup(AM10, '衣装データ'!$B:$AR, 19 + (skillLevel × 4),)    // rate (縮小倍率)。0のとき空欄化
```

`skillLevel` は所有カード登録のスキルレベル or `H32` から取得。列オフセット `16+Lv×4`〜`19+Lv×4` は Lv=1〜5 でそれぞれ `ap_skill_{Lv}_{count,per,value,rate}`（列 U〜AN）に正しく対応する。**Lv=6 に対応する列は存在しない**（列オフセット計算上 Lv=6 は列 AO=`ct_skill` を指してしまうが、`ap_skill_6_*` という概念自体が衣装データに存在しない。ゲーム内スキルLv上限が5である限り実害はない）。

#### H38 - スコアアップスキル期待値

```
H38 = IFERROR(ROUNDDOWN(IFS(
        H31 = "スコアアップ",
          IFS(OR(H33="Perfect", H33="コンボ"),
                $D8/H34 * IFS($B12=TRUE,1, $B13=TRUE,((H35+$C14)/100), TRUE,(H35/100)) * H36,
              H33="タイマー",
                $D9/H34 * IFS($B12=TRUE,1, $B13=TRUE,((H35+$C14)/100), TRUE,(H35/100)) * H36)
      )),)
```

- `$B12=TRUE` → per を 100% にする（フル発動）
- `$B13=TRUE` → per を `H35 + 10%`（`$C14=10`）にする（確率UP）
- 分母 = `$D8`（Perfect/コンボ = ノーツ数）or `$D9`（タイマー = 秒数）
- 丸め: 外側 IFS 全体を **1 回だけ ROUNDDOWN**

#### H39 - 期待縮小秒数（カード別）

```
H39 = IFERROR(IFS(
        H31 = "判定領域縮小",
          IFS(OR(H33="Perfect", H33="コンボ"),
                IF($B$15=TRUE, ROUNDDOWN($D8/H34 * H36, 0),
                               ROUNDDOWN($D8/H34 * (H35/100) * H36, 0)),
              H33="タイマー",
                IF($B$15=TRUE, ROUNDDOWN($D9/H34 * H36, 0),
                               ROUNDDOWN($D9/H34 * (H35/100) * H36, 0)))
      ),)
```

- `$B$15`（縮小フル発動）TRUE なら per を省く（確率100%扱い）
- **エラー機構**: 外側が **IFS**（`TRUE,` フォールバックなし）。`H31≠"判定領域縮小"` のとき IFS 自体が `#N/A` を返し、外側の `iferror(...,)` がそれを捕捉して空文字にする（＝**エラー経由**で空欄になる）

#### H40 - 縮小スキルスコア（カード別）

```
H40 = IFERROR(IF(H31 = "判定領域縮小",
        IFS(
          $M$6 >= 1,                                     // coverage ≥ 100%（飽和）
            IF($B$16=TRUE,
                 ROUNDDOWN($BN$23 * (H$39/SUM($H$39:$M$39)) * (H$37-1), 0),   // β: notes_20 除外
                 ROUNDDOWN($BN$22 * (H$39/SUM($H$39:$M$39)) * (H$37-1), 0)),
          TRUE,                                          // coverage < 100%（未飽和）
            ROUNDDOWN($BN$22 * H$39/$D$9 * (H$37-1), 0)
        ),
      ),)
```

- 100% キャップ時: 秒数比で按分 → 合計で `BN22 × (rate-1)`（または `BN23`）に収束
- 100% 未満時: `BN22 × (H39/D9) × (rate-1)` 相当（自分の縮小秒数を楽曲秒数で割った割合をそのまま使用。他カードとの按分なし）
- **エラー機構が H39 と異なる（重要）**: 外側が **IF**（2値分岐＋明示的な空値の第3引数）。`H31≠"判定領域縮小"` のときは IF が明示的に空の false 分岐を返し、エラーは発生しない（`iferror` は保険的に付いているだけ）
- `M6`（縮小カバー率）は 100% を超えても打ち止めにならない（クランプなし。複数枚の縮小スキルが重複すると 1.0 を大きく超えうる）
- `SUM(H39:M39)=0` のとき `M6>=1` にはなり得ない（`M6=0/D9=0<1` になるため矛盾）ので、`H39/SUM(H39:M39)` のゼロ割は実質発生しない設計だが、数式上は保護されていない

### 6-7. ラビットノートとブローチ集計（AT-AX 列、行 10-26）

ラビットノートはキャラ単位 → デッキに 1 枚でも存在するキャラの bonus を加算:

```
AT10 = '設定'!$B$13        // キャラ名（和泉一織）
AU10 = '設定'!$C$13        // Shout 加算値
AV10 = '設定'!$D$13        // Beat
AW10 = '設定'!$E$13        // Melody
AX10 = COUNTIF($AM$11:$AQ$11, "*"&AT10&"*")   // 自デッキ（AM-AQ = 5 スロット、フレンド除く）でこのキャラを含むカード数

... (AT11〜AT25 / AX11〜AX25 も同型。16人目まで)

// 集計 (フレンド枠 AR を除く)
AU26 = SUMIF(AX10:AX25, ">=1", AU10:AU25)     // Shout ラビット合計
AV26 = SUMIF(AX10:AX25, ">=1", AV10:AV25)     // Beat
AW26 = SUMIF(AX10:AX25, ">=1", AW10:AW25)     // Melody
```

**重要**: `AU26`/`AV26`/`AW26` は **3 本の独立した単一列 SUMIF**（`criteria_range` は共通で `sum_range` がそれぞれ自列のみ）。`">=1"` 条件のため、キャラが何枚デッキにいても加算は一度だけ。フレンドスロット (AR/M 列) は **カウント対象外**（`AM:AQ` のみ）。

`AX11:AX25` 自体には数式が記録されていないが、実測値（例: `AT20="百"` に対する `AX20=3`＝実際に `AM11/AN11/AO11` の3枚が「百」を含む）が `COUNTIF` 計算結果と完全一致することを確認済み。

`設定!C13:E28`（各キャラの Shout/Beat/Melody 加算値）は本ダンプでは**全セル空欄**（未設定/0扱い）。ラビットノートボーナスの実数値はユーザーが値を入力して運用する想定。

### 6-8. 登録カード候補ランキングテーブル（O4:AF204）— **v1.0.5 に記載のなかった新規文書化ドメイン**

`docs/spreadsheet-spec-v1.0.5.md` には本ドメイン（`所有カード登録` に登録した全カードを1枚単独評価してランキング表示する `O4:AF204`）への言及が一切なかった（[§15](#15-変更履歴旧版からの訂正) B2 参照）。v1.0.6→v1.0.7 間の変更でもない（`diff-report.md` で本ドメイン列は差分0件）。

```
[所有カード登録シート側への転記(FILTERスピル)]
 T4 = FILTER('所有カード登録'!M4:R1901, '所有カード登録'!B4:B1901<>"")   → T:Y に M:R がスピル
 Z4 = FILTER('所有カード登録'!Y4:AA1901, '所有カード登録'!B4:B1901<>"")  → Z:AB に Y:AA がスピル
   （T4/Z4 は実際にアンカーセルとして数式を持つ唯一のセル。U4:Y204・AA4:AB204 に対応する
     独立の数式パターンは存在しない＝スピル値）

[属性値スコア(経路②、§6-5参照)]
 AC4 = IF(P4<>"", ROUNDDOWN(Z4*$BB$33 + AA4*$BD$33 + AB4*$BF$33, 0), )

[★スキルスコア(本ドメイン)]
 AD4 = ifs(
         T4="スコアアップ",
           ifs(OR(U4="コンボ",U4="Perfect"), ROUNDDOWN( D8/V4 * W4/100 * X4, 0 ),
               U4="タイマー",              ROUNDDOWN( D9/V4 * W4/100 * X4, 0 )),
         T4="判定領域縮小",
           ifs(OR(U4="コンボ",U4="Perfect"), ROUNDDOWN( (D8/V4*W4/100*X4)/D9 * (AC4*(Y4-1)), 0 ),
               U4="タイマー",              ROUNDDOWN( (D9/V4*W4/100*X4)/D9 * (AC4*(Y4-1)), 0 )),
         TRUE, )

[合計・順位]
 AE4 = IF(P4<>"", AC4+AD4, )
 AF4 = IF(P4<>"", RANK(AE4, $AE$4:$AE$204, 0), )
```

`T4:Y4` = 所有カード登録!M:R 列（スキル種別正規化/条件/count/per/value/rate）、`Z4:AB4` = 所有カード登録!Y:AA 列（固有ブローチ込み最終 Shout/Beat/Melody）。列 `T,U,V,W,X,Y` = skill-type, condition, count, per, value, rate。

**タイマー分岐の `D9` 相殺（判定領域縮小 AD4）**: `($D$9/$V4*$W4/100*$X4)/$D$9` は数式上 `$D$9` が分子・分母で相殺され、実質 `($W4/100*$X4)/$V4` に等しい（＝タイマー条件の縮小候補スコアは楽曲秒数 `D9` に依存しない）。コンボ/Perfect分岐（`$D$8` 基準）と同じ形をコピーした際の付け忘れに見えるが、v1.0.7 の数式としてはこの通りに存在する（⚠️要確認: 意図的仕様かバグかは数式のみからは判別不能）。

丸め: 発動機会数・発動率・期待発動回数には丸めなし。`AC4`/`AD4` の最終式のみ 1 箇所 `ROUNDDOWN`。

このドメインは §6-6（`H31-H40`、現在の6枚編成用）とは**別ドメイン**で、両者は同時に現存する（混同注意）。v1.0.5 の `H31-H40` 記述の丸め位置（外側1回ROUNDDOWNか内側で都度か）等は本ドメインの `AD4`（各 `ifs` 分岐内側で個別ROUNDDOWNだが、実質1分岐しか評価されないため差はない）とは対応関係が異なる。

`衣装データ`・`固有ブローチ` を参照して所有カードの最終ステータス（特効・固有ブローチ込み）を確定する行（`r=4..204`、1行1登録カード）。列見出しと実際の突合先ドメインは**整合している**（旧稿の「見出しの直感と実際の値ドメインが逆転している」という指摘は誤りで削除。[§15](#15-変更履歴旧版からの訂正) B5 参照）。

| 列 | 内容 |
| --- | --- |
| B | 登録名 (スコア計算 H8-M8 で参照) |
| C | 名前（→ `衣装データ!D` = キャラクター名 と一致検索） |
| D | 衣装（→ `衣装データ!C` = 衣装名 と一致検索） |
| E | 特訓 (TRUE/FALSE、既定 FALSE) |
| F | 特効 |
| G | スキルレベル (1-5、空欄は 1 扱い) |
| H | カード名称（`衣装データ!D&"["&衣装データ!C&"]"`。不一致は「該当カードなし」） |
| I | 属性 (Shout/Beat/Melody) |
| J | (内部 ID、衣装データ!A) |
| K | cardID (衣装データ!B) |
| L | ap_skill_type (衣装データ!R そのまま) |
| M | スキル種別正規化（IFS） |
| N | 発動条件 (ap_skill_req) |
| O/P/Q/R | count/per/value/rate（スキルレベル別 VLOOKUP） |
| S/T/U | 属性別基礎値（自属性×未特訓の減算後） |
| V/W/X | 特効乗算後（ROUND、丸めはここ1箇所） |
| Y/Z/AA | 固有ブローチ加算後（最終値。オートフラグの行は加算対象外） |

### 計算フロー

```
[入力] C(名前) ─┐
[入力] D(衣装) ─┴→ J,K … 衣装データ!A/B を (D=C, C=D) 一致検索 → J=ID, K=cardID（不一致は "error"）
                    ↓
                    H … 衣装データ!D & "[" & 衣装データ!C & "]"（K一致で再検索、不一致は "該当カードなし"）
                    ↓
                    I … 衣装データ!K(attribute) を K 一致で取得
                    ↓
                    L … 衣装データ!R(ap_skill_type) を K 一致で取得 → M（IFSでスキル種別文字列に正規化）
                    N … 衣装データ!S(ap_skill_req) を K 一致で取得
[入力] G(スキルレベル) ─┐
                    ├→ O,P,Q,R … 衣装データ!B:AR を VLOOKUP、G(空なら1)で ap_skill_{G}_{count,per,value,rate} 選択
[入力] E(特訓) ─┐    ↓
                ├→ S,T,U … 衣装データ!M/O/Q(shout/beat/melody_max) を K一致で取得
                │          ただし「自属性(I) かつ 未特訓(E=FALSE)」なら AQ*AR(sp_time*sp_value) を減算
[入力] F(特効) ─┐    ↓
                ├→ V,W,X … ROUND(S/T/U * (1 + 設定!特効倍率(F)), 0)（C,D,F 揃った時のみ丸め適用）
                     ↓
                     Y,Z,AA … V/W/X + 固有ブローチ!G/H/I（Shout/Beat/Melody加算値、固有ブローチ!N=1のオート専用行は除外）
```

**スキル種別正規化 M（`所有カード登録` 独自の IFS。§6-6 の `H31` とは別式）**:

```
M = IFS(
  L = "スコアアップ"                                       → "スコアアップ",
  L = "MISS→Perfect"                                      → "判定ガード",
  L = "BAD以上をPerfectに変更" OR "MISS以上をPerfectに変更" → "判定強化",
  L = "判定領域を"                                          → "判定領域縮小",
  L = "判定拡大スコアダウン"                                 → "判定領域拡大",
  else                                                     → 空欄
)
```

`スコア計算!H31` 版は `TRUE, vlookup(...)` で生値パススルー（else 句が空欄ではない）に対し、`所有カード登録!M` は else 句が明示的に空欄。同じスプレッドシート内の別ドメインにある別々の正規化式（robustness が異なる）。

### エッジケース

1. **`衣装データ` 検索範囲が204行に固定**: 全 FILTER/VLOOKUP が `衣装データ!$B$2:$B204` または `$B$2:$AR204` という先頭203件のみを対象にしている。しかし `衣装データ` 実データは少なくとも2779行存在する。マスターの衣装データが203件を超えて追加された分は、`所有カード登録` の全派生列から一切ヒットしなくなる（⚠️要確認: 意図的仕様か更新漏れかは v1.0.6→v1.0.7 間で無変更という事実だけでは判定できない）
2. **`H`/`I`/`L`/`N` のエラー処理の非対称性**: `H`/`J`/`K` は `iferror(...)` で「該当カードなし」/「error」にフォールバックするが、`I`/`L`/`N` にはフォールバックが無く、無効な組合せでは #N/A のまま `S→V→Y`（`T→W→Z`, `U→X→AA`）へエラーが連鎖する
3. **`S/T/U` の非空チェック列が列ごとに異なる**（S: `C,D`／T: `D,H`／U: `H,I`）: 単純な右ドラッグなら `C,D`→`D,E` となるはずが `D,H`・`H,I` という不規則な参照（コピー時の参照ズレの痕跡の可能性）
4. **`R` 列の 0→空欄化**: `ap_skill_{G}_rate` の VLOOKUP結果が0のときは空欄にする特別処理
5. **固有ブローチの「オート」フラグ**: `固有ブローチ!N=1` の行（オート専用効果、21件）は `Y/Z/AA` の加算対象から除外
6. **`E`（特訓）未入力時**: 既定 `FALSE`（テンプレート実測値は `0`）。`S/T/U` の減算分岐は `E=FALSE` を厳密比較するため、未入力は減算対象側に入る
7. **`F`（特効）未入力時**: `V/W/X` は丸め処理をスキップし `S/T/U` をそのまま通す

⚠️要確認: `VLOOKUP(F, 設定!B6:C9, 2, )` および `VLOOKUP(K, 衣装データ!B2:AR204, idx, )` の第4引数省略（近似一致モード）が、ソートされていないキー列に対して実際に完全一致相当の結果を安定して返すのかは数式だけからは断定不可。`所有カード登録!G`（スキルレベル）のドロップダウン選択肢が1〜4か1〜5かも未確認。

## 17. 再調査時の効率的な採取手順

v1.0.7 では playwright によるセル走査ではなく、**xlsx 一括エクスポート + Python パース**を採用した。今後の再調査でも本方式を推奨する。

### 17-1. xlsx の取得と数式抽出

```bash
curl -sL "https://docs.google.com/spreadsheets/d/1UiQ-i2Ofq3DJXz0BOeFsjDId3iVrhedCL1mpIsGzNWk/export?format=xlsx" -o snapshot.xlsx
python3 tmp/spreadsheet-v107/extract_formulas.py <旧xlsx> snapshot.xlsx <outdir>
```

`extract_formulas.py` は zip 展開して `xl/worksheets/*.xml` の `<f>`（数式）/`<v>`（値）要素をパースし、行番号を `#` に正規化したパターンで版間 diff を出す。全ソースは `tmp/` 配下でコミット対象外だが、`docs/superpowers/plans/2026-07-05-spreadsheet-v1.0.7-verification.md` の Task 1 Step 2 に埋め込まれているため、再調査時はそこから復元できる。

### 17-2. `DUMMYFUNCTION` キャッシュ値ノイズの除去

Google Sheets が xlsx 非対応の関数（`FILTER`/`VLOOKUP`の一部・配列スピル等）をエクスポートする際は `=IFERROR(__xludf.DUMMYFUNCTION("<元の数式文字列>"), <キャッシュ値リテラル>)` にラップされる。この末尾リテラルは、エクスポート時点でシートに入力されていたデモカード・楽曲によって変わるため、版間で数式パターンが「別物」に見えるノイズの主因になる（`tmp/spreadsheet-v107/analyze_real_diff.py` で末尾リテラルを正規表現除去して「本質形状」だけを比較する。処理内容は「`IFERROR(__xludf.DUMMYFUNCTION("<本来の数式>"), <キャッシュ値>)` 形式から `DUMMYFUNCTION` 内の文字列（本来の数式）を取り出し、それをパターン比較の対象にする」というもので、これも `tmp/` 配下のためコミット対象外だが、処理内容自体は上記の通りなので `analyze_real_diff.py` の実体がなくても再現できる）。再調査時はこのノイズ除去を必ず行うこと。

### 17-3. 差分比較で確認すべき項目

1. `D24`・`BN21`・`BN22`・`BN23`・`M6`・`H40`・`AC4`〜`AF204` が変更されているか
2. `'設定'!B3`（バッジ）/`'設定'!C6:C9`（特効倍率）の値変更
3. 新たなブローチ種類の追加（`固有ブローチ!R` 列の値範囲、現状 1,4,5,6,7,8,9）
4. `衣装データ`/`固有ブローチ`/`所有カード登録`/`ブローチ登録` の行数変化（204行制限に到達していないか）
5. `更新履歴` シートが `IMPORTRANGE` によるライブ参照であるため、対応するバージョン行を特定できない点に注意（Phase 0 の機械diffを優先する）
